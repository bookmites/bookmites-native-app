# Part V — Putting it together

## Chapter 5.1 — End-to-end flows (stories, not a spec)

### Key vocabulary

This chapter introduces no new machinery, only a few terms worth recalling. A **flow** is the full path of one user action through the layers of the app, from a tap on the screen to bytes on the disk and back. The **adapter** is the `services/` layer that alone knows about Readium. A **locator** is Readium's description of a logical place in a book, stored as JSON. **`fileOnDevice`** is the book record's statement of whether the epub is currently on the phone. **Reflow** is the re-laying-out of text when font, size, or margins change.

### Why walk the flows

The previous four parts described the stack one component at a time: the tooling, the epub format, the reading engine, the adapter, and the data stores. Each chapter made sense in isolation, and each left the same question open, which is how the pieces behave when they work together. A component is easier to understand when you have watched it do its job in the middle of a real action, so this chapter follows three of them. The first is adding a book. The second is reading, leaving, and coming back. The third is highlighting a passage, changing the font, and reopening the book. They are written as stories, not as specifications. The exact function names and table columns will be settled in the code, and the stories deliberately avoid depending on them. What they preserve is the order of events and the reason each layer is involved, with each step tied to the chapter that explains it.

### Flow one: importing an epub

The reader taps the button to add a book. The screen that handles this belongs to the library feature, and it does not contain file-handling logic. It calls into a service that owns importing, which is the arrangement Chapter 2.3 described: features hold screens and hooks, and services hold the work that more than one feature might need.

The service asks the system's document picker to open, and the phone shows its own file chooser, not one the app drew. The reader picks a file from Downloads, or an email attachment, or a cloud drive. What comes back is not a path, but a content URI, the address Android uses to grant temporary access to a file without revealing where it lives (Chapter 4.1). The app cannot depend on that address lasting, so the next steps happen immediately.

The service generates a new `bookId`, the app's own stable identifier, and uses it to decide where the copy will go: a location inside the app's private storage, in a folder derived from the identifier. It then copies the file's bytes from the content URI to that location. This is the copy-on-import policy, and its purpose becomes concrete here. Once the copy exists, the original can move, be deleted, or become unreachable, and nothing in the library is affected.

With the file safely stored, the service reads the epub's metadata. Chapter 3.1 explained that an epub is a ZIP archive whose package file, the OPF, holds the title, the author, and the other descriptive details, so the service opens the archive just far enough to read them. If the file is malformed, this is the first place the problem appears, and the service must be ready to report it and discard the half-finished copy instead of leaving debris behind.

Finally, the service writes a book record to the SQLite database through the `db/` layer (Chapter 4.2). The record carries the `bookId`, the title and author, the path to the copy, and `fileOnDevice` set to true. The library screen, which reads from the database, then displays the new book. Notice the order. The file is written before the record, so the database never claims that a file exists when it does not. If something fails between the two steps, the worst outcome is an orphaned file, which is harmless and can be cleaned up, and not a record pointing at nothing, which would produce an error in front of the reader.

Three layers took part in this story, and each did only its own job. The feature drew the screen and responded to the tap. The service handled the picker, the filesystem, and the metadata. The database layer stored the record. At no point did Readium appear, because importing a book does not require rendering it.

### Flow two: open, read, leave, and resume

The reader taps a book in the library. The library feature navigates to the reader screen and passes the `bookId`. The reader feature's hook, of the kind shown in Chapter 3.3, calls the adapter's `openEpub` function with that identifier.

The adapter looks up the book record to find the file, and it checks that the file is really there, because the `fileOnDevice` flag is a statement and the disk is the truth. It then asks the database for the reader's saved position, a locator stored as JSON text. With the file path and the saved locator in hand, the adapter hands the file to Readium and waits. This is the publication lifecycle at work: the book moves from opening to ready, and only when Readium reports the publication is ready does the adapter resolve its promise and give the screen a session. The screen shows a loading state until then, and so it can never ask for a position in a book that is not yet open.

When the session arrives, the adapter calls `goTo` with the saved locator. Readium, a native engine under the JavaScript layer, parses the book, lays it out for this screen with the current font and margins, and displays the page containing that logical place. If the reader has never opened the book, there is no saved locator, and the book begins at the start. The reader sees the page where they stopped, and they do not need to know that nothing about "page 112" was stored anywhere. What was stored was a place in the publication, which Chapter 3.4 explained is the only kind of position that survives changes in layout.

As the reader turns pages, Readium emits a location change each time the position moves. The adapter receives these and passes them on in the app's own form, and the reader feature forwards the latest locator to a service that saves progress. Saving on every page turn would write to the database constantly, so the save is debounced: the service waits until the reader has paused or stopped turning for a short time, and then writes the most recent locator once. The write replaces the stored position for that `bookId` as a single JSON string in a `TEXT` column.

Then the reader switches to another app. Android may keep this app in memory, or may stop it entirely to reclaim resources, and the app cannot know which. This is why the save cannot wait for a graceful exit. The debounce delay is short, and the app also flushes any pending save when it is sent to the background, so that the latest position is on disk by the time the system might discard it. The user opens the app again an hour later, perhaps after the app has been completely removed from memory, and the sequence of the previous paragraphs runs once more. The adapter finds the saved locator and the book opens on the same passage.

The chain here is longer than in the import flow, and it crosses the boundary between the JavaScript layer and the native one. The feature and its hook sit in JavaScript. The adapter translates. Readium does the heavy native work of parsing and layout. SQLite stores the one fact that matters, which is the reader's place, in the form the engine itself understands.

### Flow three: highlight, change the font, reopen

The third story is the one the architecture document uses as its acceptance test, because it touches every layer and exercises the part of the stack most likely to fail.

The reader is on a page and long-presses a sentence. Readium, which owns the text on the screen and knows how it is laid out, handles the selection and reports it. It does not report screen coordinates, because those would be meaningless after the next change in layout. It reports a locator that describes the selected passage by its place in the publication. The adapter receives this event, and it surfaces it to the feature as a request that the reader may confirm, such as choosing a highlight color.

When the reader confirms, the feature asks the adapter to create a highlight, and the adapter passes the locator to Readium so that the highlight is drawn on the page. The same locator is sent to a service that stores it in the highlights table, linked to the `bookId`, together with an optional snippet of the selected text. The snippet exists only for the interface, so that a list of highlights can display words and not JSON. Remember that highlights are user artifacts (Chapter 4.1): they live in SQLite, apart from the epub, and they belong to the reader.

Next the reader opens the settings and switches to the dyslexic-friendly font, then enlarges the text. The reader feature gathers these choices and hands them to the adapter, which converts them into the settings format Readium expects, including the path to the font file. Readium reflows the book. Every line breaks differently, the page boundaries move, and the sentence that was on one page may now begin halfway down another. Here the decision to avoid pixels and page numbers pays off, because the highlight is anchored to the passage and not to a position on the screen. Readium redraws it where the passage now falls.

The reader closes the book and, the next day, reopens it. The flow of the previous section runs again, with one addition. After the adapter has opened the publication and moved to the saved position, it asks the database for the highlights belonging to this `bookId`, and it gives each stored locator back to Readium to be drawn. The reader sees the highlighted sentence in the new font and the new size, in the right place. The acceptance test in the architecture document asks for exactly this, repeated twice with different settings: change the font and size, resume, and confirm that the position and the highlight still land on the same passage on the device.

If it works, it is because of a sequence of design choices made in earlier chapters. The adapter let the feature remain ignorant of Readium. The locator was stored as the engine produced it. The file was copied so that it would still be there. The database kept the artifacts apart from the book. Failing the test usually means one of these choices was compromised, and knowing the chain makes it possible to tell where.

### What the three stories share

Looking across the flows, a pattern emerges that is worth stating directly. Each begins in a feature, which handles what the reader sees and does. Each passes through the `services/` layer, where the work is done and where the adapter hides the engine. Each ends in either the filesystem or the database, and each uses the right one: files for the large and opaque, rows for the small and structured. Readium appears only in the second and third flows, and only behind the adapter. The `bookId` is the thread that runs through all three, linking the file, the record, the position, and the highlights, and it works as a thread because it belongs to the app, not to a path or a title that might change.

This is also the best way to debug the app. A problem reported by a reader can be placed on one of these paths, and then on one step of the path. A book that will not open is a failure in the first half of the second flow, in the file or the record or the adapter. A position that resumes in the wrong place is a failure in the saving, the debouncing, or the locator. A highlight that drifts is a failure in what was stored, or in how it was handed back. The structure of the code mirrors the structure of the stories, and that is the point of having a structure.

### Common pitfalls and gotchas

The most important pitfall in this chapter is skipping the on-device test. Everything above can appear to work in a quick check on a development computer, and several of the failures that matter are invisible there. A debounced save that never fires because the app was killed in the background, a file that cannot be read because the phone's storage rules differ from the emulator's, a highlight that drifts only after the second reflow, and a font that is missing from the bundle until a release build are all problems that show themselves on a real phone and on a real book. The flows in this chapter should be run by hand, on a physical Android device, as part of finishing any change that touches them.

The related mistake is trusting the emulator alone for typography. Text rendering is the product, and emulators render it differently from phones, in sharpness, in spacing, and in how a custom font looks at small sizes. A page that reads well on a desktop screen can look cramped or uneven on the phone's real display. Layout decisions, such as margins, font sizes, and the appearance of the dyslexic font, should be judged on the device in good and poor lighting, with a long passage and not a single line.

A third pitfall is testing flows only with well-behaved books. The import flow looks flawless with a clean file from a reputable publisher. Real libraries contain books with missing metadata, odd character encodings, broken navigation, and oversized images, as Chapter 3.1 warned. A set of awkward sample files, kept on hand and run through all three flows, will reveal more than any number of clean ones.

The last pitfall is testing the parts and not the sequence. Each step in these stories may work on its own, and the failure appears only in the handoffs: the record written before the file is ready, the position saved before the publication is open, the highlight restored before the book has finished laying out. When something goes wrong, retrace the story from its first step, and look first at the moments when one layer passes work to the next.
