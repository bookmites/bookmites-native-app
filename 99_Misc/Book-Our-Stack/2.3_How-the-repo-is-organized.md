## Chapter 2.3 — How the repo is organized (features, services, db)

### Key vocabulary

A **feature** is a product area, such as the library or the reader, whose screens and supporting code are kept together in one folder. A **service** is non-visual code that does a job for the rest of the app, such as importing a file or talking to the epub engine. An **adapter** is a service that wraps an outside library so the rest of the app talks to a stable, app-specific interface instead of the library's own. A **hook** is a function, usually beginning with `use`, that lets a component read or manage state and behavior without containing that logic itself. **Design tokens** are named values for colors, spacing, and typography, such as "primary text color," that the interface uses in place of raw numbers and hex codes.

### Why structure deserves a chapter

The earlier chapters described technologies. This one describes how the team's own code is arranged around them. A tool such as Readium or SQLite is only useful if it is used consistently, and a repository's folder structure is the main way a team communicates its intentions to everyone who touches it later, including people who join after the original decisions were made. A newcomer who understands the layout can guess where a piece of code lives before searching for it, and that is a large part of working comfortably in a codebase.

The architecture document records the decisions summarized here, and the design philosophy document records the habits behind them. This chapter explains them in prose and connects them to the stack.

### The layout of `src`

The application's source lives in `03_App/mobile/src/`, and inside it the code is divided into a small number of top-level folders. The first is `features/`, which holds the product areas: `library` for the list of books and the import flow, `reader` for the reading experience, and others as they arrive. The second is `components/ui/`, which holds shared interface pieces such as buttons and text inputs. The third is `services/`, which holds code that performs work with no screen attached. The fourth is `db/`, which holds the database definition and its migrations. The fifth is `design/`, which holds the design tokens.

A sketch of the tree follows, and the exact contents will change as the app grows.

```text
src/
  components/
    ui/            shared buttons, text, list rows
  features/
    library/       library screen, import flow, hooks
    reader/        reader screen, table of contents, hooks
  services/        reader adapter, file import, storage helpers
  db/              schema, migrations, queries
  design/          design tokens
```

The comments on the right describe each folder's responsibility. The most important distinction in the tree is between `components/` and `features/`. The name `components` is reserved for pieces of interface that know nothing about the product: a button does not know whether it is in the library or the reader. Anything that exists because "Library" or "Reader" is a section of the app belongs in `features/` under that section's name. This keeps the shared folder from filling up with pieces that are secretly specific to one screen.

### Features and colocation

Inside a feature folder, everything the feature needs sits together. The screen itself is a `.tsx` file, feature-specific interface pieces sit beside it, and the hooks and helper functions, which are plain `.ts` files because they contain no interface markup, sit there too. The principle is called colocation, and the benefit is that a developer working on the reader does not hunt through five folders to follow one flow.

Hooks deserve a closer look because they are how the team keeps screens simple. A hook is a function that a component calls to obtain data and behavior. The following illustrative example shows a hook that supplies the library screen with its list of books.

```ts
export function useLibraryBooks() {
  const [books, setBooks] = useState<Book[]>([]);

  useEffect(() => {
    listBooks().then(setBooks);
  }, []);

  return books;
}
```

The function begins with `use`, which is the convention that tells React it is a hook. It declares a piece of state to hold the books, and it uses `useEffect`, a built-in hook that runs code after the screen appears. Inside the effect, it calls `listBooks`, a function that would come from the database folder, and stores the result. The component that calls `useLibraryBooks` receives a list and nothing else. It does not know that a database was involved, which is the point. The screen concerns itself with what to display, and the hook concerns itself with where the data comes from.

### Services and the import rules

The `services/` and `db/` folders hold code that is not tied to any one feature. The reader adapter, the file-import logic, and the helpers that read and write the app's private storage live in `services/`. The database schema and queries live in `db/`. Keeping them at the root, instead of inside features, reflects that more than one feature will eventually need them: the library needs to read book records, the reader needs to save positions, and later parts of the app will need both.

The folders are connected by a small set of import rules, which govern which folder may use code from which others. Stated in plain language, shared interface pieces in `components/ui` may not reach into features, because a shared button must work anywhere. Features may use shared interface pieces, services, and the database, because those are the tools features are built from. Services and the database may not import from features or from interface code, because the low-level machinery must not depend on the screens built on top of it.

The effect of these rules is that dependencies flow in one direction, from the screens down toward the machinery. This matters because circular dependencies, in which two folders each rely on the other, make a codebase hard to change: altering one part risks breaking the other. A one-way flow means a developer can modify a service without wondering whether some screen is secretly relied upon, and can rebuild a screen without disturbing the database.

### Why the reader adapter lives in `services/`

The clearest application of these rules is the reader adapter. Readium, introduced in Chapter 3.2, is accessed through a library called `react-native-readium`. The architecture document states a firm rule: features do not import Readium directly. Instead, an adapter in `services/` exposes verbs the app defines, such as opening a book, getting the table of contents, going to a location, and observing the reader's position. The reader feature calls the adapter, and the adapter calls Readium.

The reasoning is practical. Libraries change their interfaces over time, and a library's vocabulary reflects its own concerns, not the app's. If every screen spoke Readium's language directly, a change in Readium would require edits across the codebase, and any debugging of reading behavior would have to look in many places. With the adapter, there is one place to look and one place to change. Chapter 3.3 covers the adapter in detail. For this chapter, the lesson is that the layout of folders enforces a decision about where responsibility lies.

### Design tokens and thin components

The `design/` folder holds design tokens, which are named values for the visual choices the app makes. A token might be named for a role, such as primary text or a standard spacing step, and map to a particular color or number. Components then refer to the role and never to the raw value. The design philosophy document is explicit about this: raw colors, spacing values, and type sizes are not written inline, and a component's styling should read semantically, so that a name such as "primary text" appears in the code in place of a hex color.

The benefit is that a visual change, such as adjusting a color or adding a dark theme, happens in one place. For a reading app this matters more than usual, because themes and fonts are part of the product, and the same screens must look right under several of them.

The same philosophy keeps files small and components narrow. A single file should rarely exceed a couple of hundred lines, a component should do one thing and take explicit inputs, and logic that is not about drawing belongs in hooks, helpers, or services. These habits are what make the folder structure workable. A tidy tree with enormous files inside it has solved nothing, and the small-file habit keeps each piece easy to read and replace.

### Common pitfalls and gotchas

The first pitfall is the god folder, a place such as `utils` or `helpers` that gradually collects everything with no home. It starts out convenient and becomes a place nobody can navigate. The remedy is the structure above: code that serves one feature belongs in that feature, code that serves several belongs in a service or the database folder, and shared interface pieces belong in `components/ui`. When something does not fit, the right response is to name a new, specific folder, not to drop it in a catch-all.

The second pitfall is putting SQLite or Readium calls inside shared interface components. A button that queries the database, or a reusable list row that calls the epub engine, makes the shared folder depend on the machinery and violates the import rules. It also makes the component impossible to reuse in a place where that machinery is not available. Shared components should receive data and callbacks through their props, and let the feature that uses them supply the real behavior.

The third pitfall is a quiet one: a hook or helper that begins inside a single feature, gets used by a second, and stays where it started. Code that two features need has outgrown its location, and the design philosophy encourages moving it to `services/` or `db/` once the pattern is clear, rather than letting features import from each other's folders. Refactoring early, when the cost is small, keeps the one-way flow intact.
