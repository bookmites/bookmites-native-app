# Part I — The map

## Chapter 1.1 — What Bookmite Reader is building (and what "the stack" means)

### Key vocabulary

A handful of terms recur through this chapter and the rest of the book, so it helps to meet them first. A **local-first** application keeps its data on the user's own device as the primary copy, and treats any server or cloud service as optional rather than required. The **JavaScript layer** is the part of the app written in JavaScript or TypeScript, which is where most of the code the team writes will live. The **native layer** is the part written in the phone's own languages and frameworks (Kotlin and Java on Android), and it is where the heaviest work, such as drawing book pages, actually happens. An **APK** is the single installable file that Android uses to deliver an app to a phone. A **stack** is the set of technologies layered together to produce a working product, from the tools that build the app to the database that stores its data.

### Why this book exists

The Bookmite Reader project already has documents that describe what the app is for and where it is headed. Those documents answer the question of what the team wants to make. This book answers a different question: what is the machinery that makes it, and why was each piece chosen? It is a guided tour of the technology, written for someone who understands products, teams, and the shape of the web, but who has not written software in some time and has never built a native mobile app.

The tour matters because a mobile app is not a website in a smaller window. Many of the habits that carry over from web work, such as expecting to open developer tools in a browser, to edit a stylesheet, and to see the result, only partly apply. Building even a simple reading app involves a build system, an Android toolchain, a native rendering engine, and an on-device database, and each of them has its own vocabulary. A person who does not know what these pieces are will find the repository confusing and the team's technical conversations opaque. A person who does know will be able to follow a ticket, ask good questions about a tradeoff, and recognize when a problem belongs to one layer rather than another.

The book follows a deliberate order. It starts at the widest view, which is this chapter's description of what is being built and what "the stack" refers to. It then narrows through the programming model (React Native), the tools that build and run the app (Expo, Gradle, and Android Studio), the structure of the code, the epub format and the engine that reads it, and finally the data stored on the phone. By the end, the last chapters trace complete user actions through every layer, so that each piece can be seen doing its job.

### What the app does, in technical terms

The current phase of the project is deliberately small. A user can add an epub file from their phone's storage, see it in a library, open it, turn pages, jump around using the table of contents, change the reading font (including a dyslexia-friendly option), and highlight passages. When the user closes the app and returns later, the book opens at the place where they stopped. A user can also remove a book's file from the device while keeping their progress and highlights, in case they want to free space without losing their reading history.

Each of these sentences hides a technical decision. "Add an epub file from their phone's storage" raises the question of whether the app copies the file or merely remembers where it was. "Turn pages" raises the question of what software actually lays out the text and decides where each page ends. "Opens at the place where they stopped" raises the question of how a position in a book can be recorded in a way that survives the user later enlarging the font. "Keep their progress and highlights" raises the question of how a book's file and a reader's personal data can be stored separately. The chapters that follow take these questions one at a time.

The product's character also shapes the technology. The app is meant to be **local-first**: the user's reading position, highlights, and other data are stored on the phone first, and no account or cloud service is needed to read. This is a technical stance as much as a philosophical one. It means the app needs a real database on the device and a private area of the phone's storage for book files, rather than a server that holds the data and merely displays it. It also means that when something goes wrong, the explanation is almost always on the phone itself, which makes testing on a physical device unusually important.

The project is also free and open source software, which affects technology choices in a quieter way. Anyone may read the code, so tools with open licenses and active communities are preferred, and the project leans on well-known open components instead of proprietary SDKs. The epub engine described in Chapter 3.2, for example, is an open-source project used by many reading apps, not a commercial library.

### What "the stack" means

People on software teams say "the stack" to mean the pile of technologies a product rests on, each layer depending on the one beneath it. For a web application the stack might be a browser, a framework such as React, a server, and a database. The Reader has no server in its current form, so its stack is entirely on the device and in the tools that produce the app.

It helps to picture the stack in two groups. The first is the group of technologies that make up the app while it is running on a phone. At the top is the user interface, which is written with React Native, a framework for describing screens in JavaScript and TypeScript. Beneath it sits Readium, a native engine that opens epub files, divides the text into pages, and tracks the reader's position. Beside both sits SQLite, a small database built into the phone's operating system and accessed through a library called expo-sqlite, with a tool named Drizzle describing the tables. At the bottom is the phone itself, with its own file system and its own Android operating system.

The second group is the set of tools used to build the app and to work on it. Expo provides project configuration and a development workflow on top of React Native. Metro is the program that bundles the JavaScript and delivers it to a running app during development. Gradle is the build system that turns the whole project into an installable APK. Android Studio supplies the Android software development kit (SDK) and emulators that Gradle and Expo rely on, though, as Chapter 2.2 explains, it is a place the team visits rather than lives in.

None of these technologies is unusual in isolation. What makes the Reader's stack worth studying is the way they fit together, and particularly the fact that they straddle two runtimes, which is the subject of the next section.

### Two runtimes: JavaScript on top, native underneath

The single most useful mental model for this entire book is that the Reader runs as two cooperating programs inside one app. One is a JavaScript program, and the other is a native Android program. A web developer's intuition covers the first and almost none of the second, so it is worth being precise about the division.

The JavaScript layer is where the team spends nearly all of its time. Screens, buttons, the library list, the settings for fonts and themes, the logic that decides when to save a reading position, and the code that talks to the database are all written in TypeScript. This code runs on a JavaScript engine embedded in the app, not in a browser. It is edited in an ordinary code editor, and during development, changes appear on the phone almost immediately, much like refreshing a web page.

The native layer is where the work that must be fast and precise takes place. On Android this means Kotlin and Java code, compiled ahead of time, with access to the operating system's drawing and file facilities. Readium lives here. When a user sees a page of a novel, that page is drawn by native code, not by the JavaScript layer. The JavaScript layer asks for things to happen (open this book, go to this position, apply this font) and the native layer carries them out and reports back what changed.

Because the layers are separate, they communicate by passing messages across a boundary, which React Native developers often call the bridge. The details of that boundary appear in Chapter 1.2, but the following sketch conveys the flavor. It is illustrative rather than copied from the codebase, and it shows what the JavaScript side of a reading screen might look like.

```tsx
function ReaderScreen({ bookId }: { bookId: string }) {
  const [location, setLocation] = useState<string | null>(null);

  return (
    <ReaderView
      bookId={bookId}
      onLocationChange={(newLocation) => setLocation(newLocation)}
    />
  );
}
```

The first line declares a **component**, a reusable piece of screen, named `ReaderScreen`, which receives a `bookId` identifying which book to show. The second line creates a piece of remembered information, called state, which will hold the reader's current location. The returned `ReaderView` is the part that matters for this chapter's point: it looks like an ordinary web-style element, but on the phone it stands for a native view drawn by Readium. The `onLocationChange` property is a **callback**, a function that the native side calls whenever the reader turns a page, handing back the new location so that the JavaScript code can save it. The JavaScript describes what should be on screen and responds to events, while the native code does the drawing and the measuring.

This division explains several facts that would otherwise seem arbitrary. It explains why an app can feel instant when the user edits JavaScript but needs a longer rebuild when someone adds a new native library. It explains why the epub engine is not an ordinary web package that can be installed and forgotten. It also explains why a screen that runs well in a quick preview can fail on a real device: the preview may not include the native layer at all.

### Product documents and this book

The repository contains several kinds of writing, and it is worth distinguishing them. The product documents describe the project's purpose and its phases. The architecture document records technical decisions and the alternatives that were weighed. Tickets, which are written before code, record plans and history for each piece of work. This book sits beside all of these without replacing any of them. It does not restate the product vision or the roadmap, because the people who wrote those already know them. It explains the technologies, defines their vocabulary, and describes the reasoning that led the team to choose them. When the architecture document says "Expo with development builds" in one line, this book spends a full chapter on what that phrase means in practice.

Throughout, the book favors explanation of frameworks over memorization of code. Snippets appear where a concrete example clarifies an idea, and each one is followed by a description of its parts. The aim is that a reader who finishes the book can open the repository, locate the piece of the stack responsible for a behavior, and understand roughly why it was built that way.

### Common pitfalls and gotchas

The first pitfall is treating mobile development as website development. The overlap is real: React Native borrows the component model that web React uses, and TypeScript is the same language. But a phone app has no browser, no URL bar, no page reloads, and no document that exists independently of the app. Habits such as inspecting elements in a browser's developer tools, assuming styles cascade down from a global stylesheet, or expecting any page to be reachable by address will mislead. Chapter 1.2 returns to these differences in detail.

The second pitfall is assuming that the reader runs inside a browser tab. This is an easy assumption to make, because many epub readers on the web are built that way and because the underlying epub files are made of web technologies. The Reader does not work like that. Its pages are drawn by a native engine, and the app's behavior can only be fully judged on a phone or an Android emulator. A desktop browser preview, even where one is available, cannot show how fonts, page turns, or highlights truly behave.

The third pitfall is losing track of which layer a problem belongs to. A bug in a button's spacing is a JavaScript-layer concern, while a book that will not open because of a missing native library belongs to the build and the native layer. Teams save a great deal of time when they first ask which runtime is involved, because the tools for diagnosing each differ. Keeping the two-runtime picture in mind from the start is the best defense, and the rest of the book builds on it.
