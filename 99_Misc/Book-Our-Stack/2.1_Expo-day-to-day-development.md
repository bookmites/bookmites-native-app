# Part II — Building and running the app

## Chapter 2.1 — Expo: day-to-day development

### Key vocabulary

**Expo** is a toolkit built on top of React Native that supplies project setup, a development workflow, a collection of ready-made native modules, and optional cloud build services. The **managed workflow** is the way of using Expo in which the project's native Android and iOS folders are generated from configuration instead of being edited by hand. A **dev client**, short for development client, is a custom version of the app, built for the team, that loads JavaScript from the developer's computer while including whatever native code the project needs. A **config plugin** is a small piece of code that edits the generated native projects to add settings or libraries. **Prebuild** is the step that generates those native projects from the project's configuration and plugins.

### Expo as tooling on top of React Native

Chapter 1.2 described React Native as the framework that turns components into native views. React Native on its own is a library, and setting up a project with it by hand is demanding. A developer must create the Android and iOS projects, configure the build tools for each, link native libraries, and keep all of it compatible with a given version of React Native. Many teams used to spend their first week on this before writing any product code.

Expo exists to remove that burden. It is a layer of tooling and libraries that sits on top of React Native and makes the common tasks routine. It provides a command-line tool that creates a project, starts the development server, and runs builds. It provides a set of maintained native modules for common needs, such as picking a file from the phone's storage, accessing the file system, loading custom fonts, and opening a SQLite database. It provides a single configuration file in which the app's name, icon, and permissions are declared. And it provides a cloud service, called EAS, that can build the app on remote machines.

The important point for a newcomer is that Expo does not replace React Native. An Expo app is a React Native app, and the components from Chapter 1.2 are exactly the same. Expo changes how the project is set up and run, and which libraries are readily available. The architecture document records the decision to use Expo for the Reader, and records an alternative that was considered, which is bare React Native. The bare approach gives full control of the native folders from the first day, at the cost of more setup and ongoing maintenance. The team accepted Expo's conventions in exchange for a lighter daily routine.

### The daily loop

The development routine has three parts: an editor, a terminal, and a device. The editor is where code is written. The terminal is where the development server runs, started with a command such as the following.

```bash
npx expo start
```

The command `npx` runs a tool that is installed in the project, and `expo start` launches the development server, which includes Metro, the bundler introduced in Chapter 1.2. The terminal prints a QR code and a short list of keyboard shortcuts. The device, which may be a physical phone or an emulator on the computer, connects to the server, downloads the JavaScript bundle, and runs it.

From this point the cycle resembles web development. A developer edits a component, saves the file, and within a second or two sees the result on the device. The feature that enables this is Fast Refresh, which replaces the changed code in the running app and, where possible, keeps the current screen and its state, so that a developer working on the third step of a flow does not have to tap through the first two after every edit. When Fast Refresh cannot safely apply a change, such as after an error, the app reloads from the start. Most days involve nothing more than this loop: edit, save, look, adjust.

Occasional tasks are different. Adding a new library that contains native code, changing the app's permissions, or upgrading Expo's version all require a new build of the app itself, because the change affects the native layer that Metro does not deliver. These tasks are less frequent but more time-consuming, and the next sections explain why they exist.

### Expo modules

Many of the libraries a mobile app needs are not pure JavaScript. Reading a file from disk or opening a database means calling the operating system, which means native code. Expo maintains a family of such libraries, called Expo modules, each of which pairs a JavaScript interface with native Kotlin and Swift code. The Reader uses several: one for the system file picker, one for the file system, one for fonts, and one for SQLite.

These modules matter for two reasons. First, they share a release schedule with Expo itself. When a new Expo version, called an SDK version, is released, every module in the family is updated to work with it, and the team upgrades them together. Second, they are installed in a way that Expo already knows how to wire into the native projects, so the developer does not need to open Android code to use them. The cost, which later sections cover, is that the versions of Expo, React Native, and every third-party native library must be compatible with each other, so upgrades are done as a group.

### Expo Go and the development build

Expo offers a shortcut for getting started. Expo Go is an app, published in the app stores by the Expo team, that already contains a fixed set of native modules. A developer installs it, scans the QR code printed by `expo start`, and the project's JavaScript runs inside Expo Go. No native build is required, so the first run can take minutes.

The limitation is built into the design. Expo Go contains only the native code that the Expo team included when they built it. A project that needs additional native code, such as a third-party library with its own Kotlin or Swift, cannot run inside it, because the native layer is already compiled and cannot be extended. This is the situation the Reader is in. Its epub engine, Readium, is native code that lives in the library `react-native-readium`, and Expo Go has no way to include it. The architecture document states this directly: stock Expo Go is insufficient once Readium is part of the project.

The solution is a **development build**, which is a version of the app made for the team's own use. It is built from the project's native folders and so includes Readium, along with every other native dependency. It also includes a **dev client**, a developer-facing shell that connects to the Metro server just as Expo Go would. After installing a development build on a phone, the daily loop is identical to the one described above: start the server, open the app, and edit with Fast Refresh. The difference is that the app on the phone is the team's own, so it can contain any native code the project needs.

This arrangement has a useful property. The development build needs to be rebuilt only when the native layer changes. A developer who spends a week editing screens, styles, and logic does not rebuild anything. A developer who adds a native library, changes a native setting, or upgrades Expo builds a new copy and installs it, and then returns to the ordinary loop. The distinction between changes that need a rebuild and changes that need only a reload is one of the most practically important ideas in this book.

### Config plugins and prebuild

If a project includes native code, where does that code live? In a bare React Native project, it lives in two folders named `android` and `ios`, which developers edit by hand. In Expo's managed workflow, those folders are generated from the project's configuration, and the developer does not usually edit them directly.

The generation step is called **prebuild**. It reads the project's configuration file and the list of installed libraries and creates the native folders from them. Libraries that need special native setup, such as an added line in an Android build file or an entry in an iOS configuration, ship a **config plugin**, a small program that Expo runs during prebuild to make those changes. The Reader's project lists such plugins in its configuration, in a form that looks like the following. As elsewhere in this book, the snippet is illustrative and the repository holds the actual file.

```json
{
  "expo": {
    "name": "Bookmite Reader",
    "plugins": [
      "expo-sqlite",
      "expo-document-picker",
      "react-native-readium"
    ]
  }
}
```

The `name` entry is what appears under the app's icon on the phone. The `plugins` list names libraries whose config plugins should run during prebuild. When the command runs, each plugin makes its edits to the generated Android and iOS projects. Readium requires several such edits: the Android build needs a specific Java version, JDK 17, and a setting called desugaring that allows newer Java features on older Android versions, and the iOS project needs its own dependency setup. By expressing these as plugins, the project keeps the changes in configuration that can be reviewed, reproduced, and regenerated, instead of in hand-edited native files that are easy to lose or forget.

The practical consequence is that the native folders are treated as output, not as source. If something goes wrong with them, the usual remedy is to regenerate them from configuration. This is the reason the architecture document says the native setup is persisted through prebuild and config plugins.

### Building the app: a pointer to what follows

A development build is produced by running a command such as the following.

```bash
npx expo run:android
```

This command runs prebuild if needed, compiles the Android project with Gradle, installs the result on a connected phone or emulator, and starts the app. Chapter 2.2 explains what Gradle does and what an APK is. For this chapter it is enough to know that Expo orchestrates the process and that Gradle performs the compilation.

Expo also offers EAS, its cloud build service, which performs the same compilation on remote machines and returns the finished file. The team may use it when building locally is inconvenient, for example when a teammate lacks the Android tools or when a build should be produced in a clean, repeatable environment. For day-to-day work on a single Android machine, local builds with Gradle are the main path, and EAS is a tool for occasions when it helps.

### What is daily and what is occasional

It helps to separate the frequent activities from the rare ones. Daily, a developer edits code, runs `expo start`, and watches the result on a device through Fast Refresh. This involves only the JavaScript layer and Metro. Occasionally, when a native dependency is added or changed, when Expo is upgraded, or when a configuration setting that affects the native projects is edited, a developer runs prebuild and builds a new development build. This involves Gradle, the Android SDK, and several minutes of waiting. Rarely, when something in the native folders is truly broken, a developer opens Android Studio to inspect it, a scenario Chapter 2.2 describes.

Seeing the work this way prevents a common source of frustration. A newcomer who expects every change to appear instantly will be surprised when a new library requires a rebuild, and a newcomer who rebuilds after every edit will waste hours. Knowing which category a change belongs to is most of the skill.

### Common pitfalls and gotchas

The first pitfall is expecting every dependency to work in Expo Go. A library that contains native code will either fail to load or produce an error about a missing native module when run in Expo Go. The error is not a bug in the library or the project. It means that the app on the phone does not contain the native code the project needs, and the fix is to use a development build.

The second is confusing a native rebuild with a JavaScript reload. If a developer installs a library with native code and only reloads the app, the new library will not be present, because the installed app was built before the library was added. The symptoms are usually errors about a module that cannot be found. The rule is that any change to native dependencies, native configuration, or the Expo version requires building and installing the app again, while changes to ordinary code require only a refresh.

The third is version coupling. Expo's SDK version, React Native's version, and the versions of native libraries such as `react-native-readium` must be compatible with each other. Upgrading one without checking the others is a frequent cause of builds that suddenly fail. The architecture document lists this explicitly as a tradeoff the team accepted, and the sensible habit is to upgrade as a group, consult the release notes, and run the app on a physical device afterward.

The fourth is editing the generated native folders by hand and then regenerating them. Because prebuild produces those folders from configuration, a manual change can be overwritten the next time prebuild runs. If a native setting must change, the change belongs in the Expo configuration or in a config plugin, so that it survives regeneration.
