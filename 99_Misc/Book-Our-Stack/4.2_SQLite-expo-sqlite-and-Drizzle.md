## Chapter 4.2 — SQLite, expo-sqlite, and Drizzle

### Key vocabulary

**SQLite** is a small, self-contained database engine that stores an entire database in a single file and runs inside the app itself. A **schema** is the definition of a database's tables and columns. A **migration** is a versioned, recorded change to the schema, applied in order so that every copy of the database reaches the same structure. **expo-sqlite** is Expo's library for using SQLite from a React Native app. **Drizzle** is a library that describes the schema in TypeScript and produces typed queries and migrations. **Debounce** means delaying an action until a burst of triggers has stopped, so that it runs once instead of many times. A **foreign key by `bookId`** is a column in one table that refers to the book in another, linking the two.

### What SQLite is on a phone

A web developer's picture of a database is usually a server: a separate program, often on another machine, that an application connects to over a network. SQLite is a different kind of thing. It is a library that lives inside the app, and the whole database is one file on the phone's storage. There is no server to run, no connection to configure, and no network involved. The app opens the file, runs queries against it, and closes it.

This simplicity is why SQLite is the standard choice for local data on mobile. Android and iOS both ship it, and it is among the most widely deployed pieces of software in the world. It supports the familiar ideas of a relational database: tables with typed columns, rows, indexes for fast lookup, queries written in SQL, and transactions that make a group of changes succeed or fail together. For the Reader's purposes it holds the library index, the reading positions, the highlights, and the settings, the structured data described in Chapter 4.1.

The choice also follows from the product's character. A local-first app needs a real database on the device, because the phone is where the truth lives. A server-backed design would have put that role elsewhere.

### Why not just JSON files?

A reasonable question is why the app does not simply save its data as JSON files, which are easy to write and read. For a handful of values, that would work. The difficulty appears as the data grows and as the app needs to do things with it.

Consider the highlights. A reader may create hundreds across many books. The app needs to list the highlights for one book, show them in order, delete one, and eventually search them. With JSON files, each of those operations means reading a whole file into memory, changing it, and writing it back, and a crash in the middle of writing can corrupt the file. A database handles these tasks natively. It finds the rows it needs without loading everything, it changes one row without rewriting the rest, and it protects against half-finished writes through transactions.

Relationships are the second reason. Highlights belong to books, and positions belong to books, and a library screen may want to combine information from several tables. A relational database expresses these links directly. With files, the app would have to maintain the connections by hand, and mistakes there are the kind of bugs that take weeks to notice.

The last reason is change over time. An app that is updated across many releases will need to add fields and tables, and the data on readers' phones must be carried forward intact. A database with migrations gives a disciplined way to do so. Ad hoc files make every format change a new compatibility problem.

### The driver and the ORM

Two separate pieces of software cooperate in the Reader's data layer, and keeping them distinct helps in understanding the stack. The first is the driver, which is the code that actually talks to SQLite. The second is the layer on top, which helps the developer describe and query data in a more convenient way.

The driver is expo-sqlite, Expo's own binding for SQLite in React Native. It is a native module, like the others in Chapter 2.1, with a JavaScript interface for opening a database and running SQL. By itself it is workable but low-level, and the developer writes SQL as strings and receives untyped results.

The layer above is Drizzle, which is an ORM, or object-relational mapper, although a light one. It lets the developer describe tables in TypeScript, so that the schema is code that the compiler can check, and it provides a query interface whose results carry types. If a query asks for a column that does not exist, the editor reports an error immediately and not when a reader hits it at runtime. Drizzle also generates migrations from changes in the schema. The pairing is recorded in the architecture document as the decision: expo-sqlite as the driver, Drizzle for schema, types, and migrations, both living in `db/`.

The document also names an alternative, op-sqlite, a different driver that is often faster and is popular in performance-sensitive apps. It was not chosen for now, for reasons that are practical and not ideological. The Reader's database load in this phase is modest, a library list, debounced position saves, and highlights, so raw speed rarely matters. Expo's own library follows the same upgrade path as the rest of the Expo SDK, adds one fewer native dependency while Readium is already a heavy integration, and has documented behavior with development builds. Because Drizzle sits above the driver, switching later would change the connection code and leave the schema and queries mostly intact. The team commits to revisiting the choice only if measurements show the database causing trouble on a device.

### An example schema

A short, illustrative schema shows how the tables from Chapter 4.1 might be written with Drizzle. The real definitions will be settled during the first integration.

```ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core';

export const books = sqliteTable('books', {
  bookId: text('book_id').primaryKey(),
  title: text('title').notNull(),
  author: text('author'),
  filePath: text('file_path'),
  fileOnDevice: integer('file_on_device', { mode: 'boolean' }).notNull(),
});

export const positions = sqliteTable('positions', {
  bookId: text('book_id').primaryKey().references(() => books.bookId),
  locator: text('locator').notNull(),
  updatedAt: integer('updated_at').notNull(),
});

export const highlights = sqliteTable('highlights', {
  id: text('id').primaryKey(),
  bookId: text('book_id').notNull().references(() => books.bookId),
  locator: text('locator').notNull(),
  snippet: text('snippet'),
  createdAt: integer('created_at').notNull(),
});
```

Each `sqliteTable` call defines one table, naming the table in SQL and listing its columns. The `books` table has a `bookId` as its primary key, which means the value uniquely identifies each row, and the `title` is marked `notNull`, so a row cannot exist without one. The `author` and `filePath` are allowed to be empty. SQLite has no true boolean type, so `fileOnDevice` is stored as an integer and Drizzle is told to present it in code as a boolean.

The `positions` and `highlights` tables show the relationship between records and artifacts. Each has a `bookId` column that `references` the `books` table. This is a foreign key, a declaration that the value must match a real book, and it is the formal version of the link described in Chapter 4.1. The `locator` columns are plain `text`, which is where the serialized locator JSON from Chapter 3.4 is stored, and the `snippet` in `highlights` is the optional display text. The timestamps are stored as integers, a common compact representation of a date.

### Migrations from the first schema

A migration is a recorded step that changes the database's structure from one version to the next. The first migration creates the tables above. If a later release adds a column for a second locator, or a table for notes, that is another migration. Each is saved as a file, numbered in order, and the app applies any that a given phone's database has not yet received when it starts.

The practice matters from the first day because the app will be installed on phones before the schema is final. A reader who installed an early version has data in the old structure. Without migrations, the only options for a changed schema are to erase that data or to leave the app broken. With migrations, the app brings the old database forward step by step and the reader's highlights remain. The architecture document sets the rule that migrations begin with the first schema, and not as something added later.

In Drizzle's workflow, the developer edits the TypeScript schema and runs a command that compares the new schema with the previous state and writes a migration file. The app includes those files and runs them at startup, before any screen reads data. The process is mechanical, and its value lies in the discipline of never changing the database structure by hand.

### Storing locator JSON in a text column

The `locator` columns above hold JSON as plain text, a design decision that follows from Chapter 3.4. The locator is a structured object that the engine produces and consumes whole. The app does not query inside it, since nothing needs to ask for all highlights whose progression exceeds a certain value. Storing it as a single text value keeps the schema small and keeps the adapter, not the database, as the only code that understands its shape.

The cost is that the database cannot easily search within a locator, which is why the snippet is stored as a separate column when text-based listing or search is needed. This is a deliberate division: the locator is for finding the passage, and the snippet is for showing it.

### Debounced position saves

Position tracking raises a practical question. The reader's location changes whenever a page is turned, and the engine reports each change through a callback. If the app wrote to the database on every change, it would perform a write for each page, and while one write is cheap, a rapid sequence during a quick skim is wasteful.

The remedy is a debounce, which waits until the events stop before acting. The following illustrative function shows the idea.

```ts
let timer: ReturnType<typeof setTimeout> | undefined;

export function savePositionDebounced(bookId: string, locator: string) {
  if (timer) clearTimeout(timer);
  timer = setTimeout(() => {
    savePosition(bookId, locator);
  }, 1000);
}
```

Each call cancels any waiting timer and starts a new one. Only when a full second passes with no new call does the timer fire and perform the save. A reader turning pages quickly causes many calls and one write, and a reader who pauses causes a write after the pause. The tradeoff is that a position change in the final second before the app is closed may be lost unless the app also saves when it moves to the background, which is the kind of detail that the first integration will test. The architecture document identifies debouncing as one of the ways the project keeps heavy traffic off the database, and as the reason it accepts expo-sqlite's slightly smaller performance headroom.

### Common pitfalls and gotchas

The first pitfall is neglecting migrations. A project that edits the schema in place during early development, and plans to add migrations later, will find that later is when the data of real users is at stake. Beginning with migrations costs little, and the history it records is valuable.

The second pitfall is running heavy queries on the JavaScript thread. Chapter 1.2 explained that the interface depends on a single thread, and a slow query that blocks it will freeze the screen. Synchronous database calls are convenient but should be limited to small, quick operations. Larger work should use the asynchronous interface so that the thread stays free to respond to touches.

The third is duplicating book rows on re-import. If a reader imports the same file twice, the current design creates two book records with two copies of the file, since each import generates a new `bookId`. The architecture document marks de-duplication, by comparing a hash of the file's contents, as left for later. Until it exists, the app should be prepared for duplicates and not assume one row per title.

The last is a quiet one: treating the database as unchanging between releases. Any developer who adds a column and tests only on a fresh install may never see the failure that appears on a phone with older data. Testing the upgrade path, by installing an earlier build, creating data, and then installing the new one, is the check that catches it.
