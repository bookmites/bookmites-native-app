## Chapter 3.3 — The reader adapter (`EpubSession` / `readerEngine`)

### Key vocabulary

An **adapter** is a layer of code that sits between the app and an outside library and translates between the two, so that the app speaks only its own vocabulary. **`goTo`** is the adapter's verb for moving the reader to a given location, such as a saved position or a table-of-contents entry. The **publication lifecycle** is the sequence a book passes through in the reader: not yet opened, opening, ready, and closed. **Decoupling** means arranging code so that one part can change without forcing changes in another.

### The problem the adapter solves

Chapter 3.2 introduced `react-native-readium`, a library that lets the app display a Readium navigator and talk to it. It would be possible to use that library directly wherever the app needs to read a book: the reader screen would render the Readium component, the table-of-contents screen would read the publication's data, the highlight feature would call whatever selection functions the library provides, and the position-saving code would handle the locators it emits.

This works at first and becomes a burden over time. Readium's names, data shapes, and behavior are the library's own, and they reflect its design choices, not the app's. When the library releases a new version that renames a property or changes the shape of a locator, every place that touched it must be found and fixed. When a reading bug appears, the cause might be in any of those places. Worse, each screen must learn Readium's concepts to use them correctly, so the knowledge needed to work on the app spreads across the whole codebase.

The adapter is the standard remedy. It is a thin layer, living in `services/`, that exposes the operations the app wants in the app's own terms, and it is the only code that knows about Readium. Everything else in the app talks to the adapter. The architecture document states the rule simply: features do not import Readium directly, and the reader adapter exposes app-level verbs.

### The adapter pattern in product terms

A useful way to think about the adapter is to separate what the product needs from how an engine provides it. The product needs to open a book, show its table of contents, jump to a place, know when the reader's place changes, and create and list highlights. These are verbs a product designer would recognize, and they remain true whether the engine underneath is Readium, a different library, or a future replacement. Readium's way of doing each of them is a detail of implementation.

The adapter's surface is therefore a short list of operations. It opens and closes a publication for a given book. It provides the table of contents in a form the interface can display. It offers a `goTo` operation that accepts a location, and it lets other code observe the reader's location as it changes. It creates and lists highlights, each tied to a location. Later, it is expected to supply the text surrounding a location, so that a future AI feature can be given the passage a reader is looking at. That last item is mentioned in the architecture document as a future need, and it is noted here only because it explains why the adapter is built as a general layer and not as a screen helper.

The names `EpubSession` and `readerEngine` are used in the project's documents for this layer, and the architecture document says either is acceptable. The word "session" is apt, because the adapter represents one open book: from the moment the reader opens it until the moment the reader leaves, a single session object knows which book is open, where the reader is, and how to move around. The object is the middle box in a simple picture, with the app's screens on one side and Readium on the other.

### A small example

The following sketch shows how the pieces relate. It is illustrative, since the real code will be shaped by the project's decisions as the reader is built.

```ts
// services/reader/EpubSession.ts
export type EpubSession = {
  toc: TocEntry[];
  goTo: (location: Locator) => void;
  onLocationChange: (listener: (location: Locator) => void) => void;
  close: () => void;
};

export function openEpub(bookId: string): Promise<EpubSession> {
  // looks up the stored file, hands it to Readium,
  // and resolves when the publication is ready
}
```

This file defines what a session offers and how to start one. The `EpubSession` type lists the verbs: a `toc` that holds the table-of-contents entries, a `goTo` function that accepts a location, a way to subscribe to location changes, and a way to close the session. These names belong to the app. The function `openEpub` takes a `bookId`, which is the app's own identifier for a book, and returns a promise, a JavaScript value that stands for a result that will arrive later. The comment explains what happens inside, which is the adapter's real work: finding the book's file, handing it to Readium, and waiting for the publication to be ready. The promise resolves only when the book is open, so any code holding a session can rely on it being usable.

A feature then uses the adapter without any knowledge of Readium.

```ts
// features/reader/useReaderSession.ts
export function useReaderSession(bookId: string) {
  const [session, setSession] = useState<EpubSession | null>(null);

  useEffect(() => {
    let current: EpubSession | null = null;
    openEpub(bookId).then((s) => {
      current = s;
      setSession(s);
    });
    return () => current?.close();
  }, [bookId]);

  return session;
}
```

This hook, which lives in the reader feature, opens a session when the screen appears and returns it. The `useEffect` call runs the opening logic when the `bookId` is set or changes, and the function it returns is cleanup code that React runs when the screen goes away. In that cleanup, the hook closes the session, which is how the publication's lifecycle is tied to the screen's. The screen that calls this hook receives either nothing, while the book is opening, or a session it can use. Nothing in the hook names Readium, and replacing the adapter's contents would not require editing it.

The chain of responsibility is the point of the example: the feature calls the service, and the service calls Readium. Each link knows only its neighbor.

### The publication lifecycle

A book in the reader passes through stages, and the adapter is the natural place to manage them. Before anything happens, no book is open. When the reader requests one, the book is opening: the file is being read, parsed, and prepared. Once Readium reports the publication is ready, the book is open, and navigation, table-of-contents requests, and position tracking are meaningful. When the reader leaves, the book must be closed, releasing its resources.

Treating this as an explicit lifecycle prevents a class of errors. The most common is acting too early, such as asking to jump to a location before the publication is ready, which Chapter 3.2 listed as a pitfall. If the adapter only hands out a session once the book is ready, the rest of the app cannot make that mistake. A second error is forgetting to close, which leaves a native view and its memory in use after the reader has gone. Placing the close in the hook's cleanup, as above, ties it to the screen reliably.

### What the adapter hides

The adapter's value is clearest in what it keeps out of the rest of the code. Readium describes locations as locator objects, with fields and nesting that follow its conventions. A screen that receives these objects must understand them, and if it parses them to find a chapter or a percentage, that parsing is now duplicated across the codebase, and every copy must change if the format does. The adapter confines this. It may expose the location as an opaque value that other code stores and returns without inspecting, plus a small number of helpers for the things the interface needs to show, such as a progress percentage.

The same applies to the structure of the table of contents, the settings format, the selection events for highlights, and the timing of callbacks. Each is translated once, in the adapter, and presented in a consistent form. The benefit is not only protection against change. The adapter also offers a single place to debug reading behavior. When a reader reports that the book opened at the wrong place or that a highlight misbehaved, there is one layer in which to add logging and to look.

The architecture document is candid about the limits of this idea. It states that swapping the engine is out of scope now that Readium is chosen, so the adapter is not a promise that the engine could easily be replaced. Its purpose is narrower and more practical: it limits the blast radius when Readium's interface changes or when the team's use of it changes.

### Common pitfalls and gotchas

The most tempting mistake is a feature importing `react-native-readium` directly. It usually happens under time pressure, when a screen needs one small thing from the library and the adapter does not offer it yet. The shortcut works, and it also breaks the structure, because now that screen depends on Readium's shapes, and the next developer will copy the pattern. The better habit is to add the missing verb to the adapter, even if it is a single line, and let the feature call that. The import rules of Chapter 2.3 exist to make this an easy habit to keep.

The second pitfall is leaking locator parsing into screens. A screen that reads fields out of a locator to compute a chapter name or a progress figure has taken on knowledge that belongs to the adapter. If the locator's shape changes, the screen breaks in a place no one would think to look. The adapter should provide the derived values the interface needs, so that screens never need to look inside a location.

The third pitfall is designing the adapter too large. An adapter that copies every function the library offers is only a second copy of the library, with the same exposure and more code. The best adapters are small and shaped by what the product actually uses. The surface listed in this chapter is deliberately short, and it should grow only when a real feature requires another verb.

The last is forgetting that the session has a lifetime. Holding on to a session after the book has been closed, or using one while a new book is still opening, leads to confusing behavior. Keeping the session's creation and closing in one hook, as in the example, limits the places where this can go wrong.
