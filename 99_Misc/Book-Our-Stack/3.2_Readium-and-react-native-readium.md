## Chapter 3.2 — Readium and `react-native-readium`

### Key vocabulary

**Readium** is an open-source toolkit for reading digital publications, which includes the engine that parses epubs, lays out their text, and tracks the reader's position. A **publication** is Readium's name for a book once it has been opened and understood: its metadata, its reading order, and its table of contents, held in memory. A **navigator** is the component that displays a publication and responds to page turns, selection, and settings. A **locator** is Readium's description of a specific place in a publication, introduced here and explored fully in Chapter 3.4. A spine item's **`href`** is the path of one content file within the book, and it forms the first part of every locator.

### What Readium is

Chapter 3.1 described what an epub contains. Turning that container into pages on a screen is a large task, and it is the task Readium performs. A reading engine must open the archive, parse the package document and the table of contents, load each chapter, apply the book's styles together with the reader's chosen settings, divide the flowing text into pages, respond to taps and swipes, let the user select and highlight text, and report where the reader is. It must do all of this quickly and correctly across thousands of books produced by uneven tools. Writing such an engine from scratch would take a team years.

Readium is the established answer. It is an open-source project, maintained by a nonprofit consortium, that has been used in many commercial and public-interest reading apps. It exists as separate toolkits for different platforms, with a Kotlin implementation for Android and a Swift implementation for iOS. Each toolkit provides the parsing, layout, pagination, and navigation described above, and each pays attention to accessibility, so that screen readers, adjustable text, and alternative fonts work as they should. For a project that wants to be accessible and to support a dyslexia-friendly typeface, an engine with accessibility as a design priority is valuable, not merely convenient.

In the vocabulary of the stack, Readium sits in the native layer. It is Kotlin code on Android and Swift code on iOS, and it draws the pages. The JavaScript layer never lays out text itself.

### Native navigator versus WebView and epub.js

Two broad approaches exist for displaying an epub inside a mobile app, and the architecture document records the choice between them.

The first approach wraps a web page. A WebView is a component that embeds a browser engine inside an app, and a library such as epub.js is a JavaScript program that, running within that browser, reads an epub and renders its chapters as web pages. This approach is quick to prototype, because the web is a familiar environment and the library is widely used. Its weaknesses show up in the details that matter for reading. Pagination is approximated by splitting the web page into columns, which can behave unpredictably as fonts and margins change. Anchoring a highlight to text that later reflows is harder, and accessibility depends on how well the embedded browser and the library cooperate. The result is, in the document's words, closer to a browser in a box than to a reading experience.

The second approach is a native navigator, the approach Readium takes. Here, the engine's own code lays out and draws the pages using the platform's native facilities, although for epubs the underlying rendering of each chapter's HTML still uses a web view internally, wrapped by Readium's carefully built pagination, selection, and position-tracking logic. This distinction is subtle but important: the project does not sit a generic web page library on top of a WebView and hope for the best. It uses an engine whose whole purpose is the reading experience, and which exposes positions and selections in a form designed for lasting records.

The team chose Readium for those reasons: better pagination and selection behavior, an industry-standard way of describing positions that remains stable when users change fonts, and a sound foundation for dyslexic fonts, table-of-contents navigation, and, later, giving an AI feature the text around a reader's current location. The accepted cost was a heavier integration and a steeper learning curve, since the team must learn Readium's concepts, and the engine cannot run inside Expo Go, as Chapter 2.1 explained.

### `react-native-readium`: connecting the layers

Readium's toolkits are written for Kotlin and Swift, and the Reader's interface is written in React Native. A connecting library is needed so that JavaScript code can display a Readium navigator and talk to it. That library is `react-native-readium`, an open-source package that provides a native view, which appears in JavaScript as an ordinary component, together with a small interface for controlling it.

A web developer might compare it to a wrapper that lets a framework use a third-party widget. The wrapper contains native code that creates the real Readium navigator on each platform, and it exposes a component with properties and callbacks that React code can use. Chapter 1.1 previewed this pattern with a `ReaderView`. The following sketch shows the same idea more concretely. The exact names of properties vary with the library's version, so the snippet is illustrative, and the repository's code and the library's documentation are the authorities.

```tsx
<ReadiumView
  file={epubPath}
  location={savedLocator}
  settings={{ fontSize: 120, theme: 'sepia' }}
  onPublicationReady={(publication) => setToc(publication.tableOfContents)}
  onLocationChange={(locator) => saveLocator(locator)}
/>
```

Each property carries one idea. The `file` property tells the navigator which epub to open, and it receives a path in the app's private storage, consistent with the copy-on-import policy of Chapter 3.1. The `location` property says where to open, and it receives a locator that the app saved earlier, so a returning reader resumes where they stopped. The `settings` property carries the reader's preferences, such as text size and theme, and it is also the route by which a different font, including the dyslexic font, reaches the engine. Changing a setting does not reload the book. The navigator re-lays out the same content under the new settings.

The two callbacks are how the native side reports back. `onPublicationReady` fires once Readium has opened the epub and understood it, and it hands back the publication's information, including the table of contents the interface needs for navigation. A screen should not try to show a table of contents or jump to a location before this moment, because until it fires there is no publication to ask. `onLocationChange` fires whenever the reader's position changes, such as after a page turn, and it hands back a locator. The app's job is to save it, and as Chapter 4.2 explains, to save it sparingly and not on every event.

### Locators and spine items, a first look

The locator that appears in the snippet is the most important concept in this chapter. A locator is a small piece of structured data, in JSON, that describes a place in a publication. At minimum it names the spine item the reader is in, by its `href`, and it may also carry a progression, which is how far through that item the reader has gone, and further details that pin down the position more precisely. Because it describes a position by reference to the book's content and not to the screen, it remains meaningful after the font changes. An illustrative locator looks like this.

```json
{
  "href": "chapter-02.xhtml",
  "type": "application/xhtml+xml",
  "locations": {
    "progression": 0.42,
    "totalProgression": 0.18
  }
}
```

The `href` identifies the content file, matching the spine entry covered in Chapter 3.1. The `progression` says the reader is forty-two percent of the way through that file, and the `totalProgression` says they are eighteen percent of the way through the whole book. Nothing in the object mentions pixels, pages, or screen sizes, and that omission is deliberate. Chapter 3.4 explains what else a locator can contain and why this form was chosen for storing progress and highlights.

### Nitro modules, at a high level

The architecture document mentions that Readium's integration brings in Nitro modules, and it is worth understanding at a general level what that means. In the earlier discussion of the bridge, the JavaScript and native layers were described as two worlds with a channel between them. Nitro is a newer technique for building that channel. It lets native code be exposed to JavaScript with less overhead and with generated, type-safe interfaces, so that calls between the layers are faster and less error-prone than under older approaches.

For a reader of this book, the consequence is mostly practical. Nitro modules are native code, which is one more reason the engine requires a development build and cannot run in Expo Go. They also add to the native dependencies that must stay compatible with the project's Expo and React Native versions. Beyond that, the mechanism is not something the team writes or maintains, and the book does not go deeper.

### Expo integration friction

Integrating a native engine into an Expo project is the most demanding part of the stack's setup, and the architecture document lists it as the first risk. This book does not provide a tutorial, since the specifics change with each version, but it is useful to know the kinds of friction involved.

On Android, Readium needs a recent Java version, JDK 17, and it relies on a Java feature that older Android versions lack, which the build must supply through desugaring, as Chapter 2.2 described. It also requires a compile SDK version at or above a certain level. On iOS, native dependencies are installed through a tool called CocoaPods, and the project's pod configuration must include Readium's libraries. In an Expo project these changes are not made by hand in the native folders. They are expressed through config plugins and applied during prebuild, as Chapter 2.1 explained, so that they survive regeneration of those folders.

The friction is concentrated early. Once the dev build compiles and the navigator displays a book, day-to-day work returns to the ordinary loop. The architecture document's plan for the first integration is a spike, a short and focused experiment, in which the team checks that a book opens, that a position can be saved and restored, and that a highlight survives a font change, all on a real device. Treating the integration as a spike prevents the team from building features on a foundation that has not been shown to work.

### Common pitfalls and gotchas

The first pitfall concerns highlights and positions. A developer unfamiliar with reflowable text may be tempted to remember a highlight by the screen coordinates at which it was drawn, or a position by a scroll offset. This works until the reader changes the font size, at which point every coordinate is wrong, and highlights drift away from the words they marked. The remedy is to store what Readium provides, a locator that refers to the content, and to treat anything that depends on screen layout as temporary.

The second pitfall is underestimating the native build setup. The integration looks small from the JavaScript side, since it is a component and a few callbacks, but behind it are Gradle settings, Java versions, iOS pods, and version constraints between Expo, React Native, and Readium. Build errors in this area are often unfamiliar to people who have worked only with JavaScript, and the messages may point to files the developer did not write. Allowing time for the integration, reading error messages for the mention of versions, and keeping the setup in config plugins and not in hand edits will save effort.

The third is acting before the publication is ready. The navigator is created asynchronously, and requests such as jumping to a location or reading the table of contents only make sense after `onPublicationReady` has fired. Code that assumes the book is open as soon as the component appears will fail intermittently, in ways that depend on how fast the device is.

The last pitfall is speaking Readium's language everywhere in the app. The library's property names and data shapes can change between versions, and a screen that depends on them directly will break when they do. Chapter 3.3 describes the adapter that the project places between the app and the library to keep that exposure in one place.
