# Part III — Epubs and the reader engine

## Chapter 3.1 — Epub for implementers (not publishers)

### Key vocabulary

**Epub** is the open file format for reflowable digital books. The **OPF**, or Open Packaging Format file, is the book's master document, listing its metadata, its files, and its reading order. The **spine** is the ordered list inside the OPF that says which content files make up the book and in what sequence a reader moves through them. **NCX** and the **nav document** are the two formats epub uses for a table of contents: NCX in the older Epub 2, and a nav document, written in XHTML, in Epub 3. **XHTML** is a strict version of HTML that follows the rules of XML. A **reflowable** book lets the reading app decide how text is broken into lines and pages, in contrast to a fixed-layout book, whose pages are laid out in advance. A **sandbox** is the private area of storage that Android assigns to each app, and other apps cannot normally read it.

### A perspective for implementers

Most writing about epub is aimed at publishers, who make books and care about typography, metadata, and distribution. This chapter takes the opposite view. The Reader does not create epubs. It receives them, from sources it does not control, and must open each one reliably. The relevant questions are therefore what an epub file contains, what a reading engine must understand to display it, and what can go wrong when the file is not what the specification says it should be.

A web developer will find the territory familiar. An epub is, at heart, a small website packed into a single file. Its pages are HTML, its styling is CSS, and its images are ordinary images. What makes it a book is the extra structure that tells a reader how the pages are ordered, how they are named, and how to navigate them.

### An epub is a ZIP file

An epub file is a ZIP archive with the extension `.epub`. Renaming a copy to `.zip` and opening it with any archive tool reveals a folder structure. The typical contents look like the following.

```text
mimetype
META-INF/
  container.xml
OEBPS/
  content.opf
  toc.ncx
  nav.xhtml
  chapter-01.xhtml
  chapter-02.xhtml
  styles/
    book.css
  images/
    cover.jpg
```

The file named `mimetype` declares the file's type and contains the single line `application/epub+zip`. The `META-INF` folder contains `container.xml`, which does one job: it points to the location of the OPF file. The folder name `OEBPS` is a convention, and publishers may use other names, so a reader never assumes a path and always follows the pointer in `container.xml`. The rest are the book's content: chapters as XHTML files, stylesheets, images, and the table-of-contents files.

This arrangement explains how a reading engine begins. It opens the ZIP, reads `container.xml` to find the OPF, reads the OPF to learn what the book contains and in what order, and then loads content files as the reader moves through them. The engine does not need to unpack the whole book to disk first, because ZIP archives permit individual files to be read directly.

### The OPF: metadata, manifest, and spine

The OPF is an XML document with three principal parts. The metadata section holds the title, author, language, and identifier. The manifest lists every file that belongs to the book, giving each an identifier, a path, and a media type. The spine lists, in order, the identifiers of the content files that form the book's main reading sequence. A simplified example follows.

```xml
<package xmlns="http://www.idpf.org/2007/opf" version="3.0">
  <metadata>
    <dc:title>Example Book</dc:title>
    <dc:language>en</dc:language>
  </metadata>
  <manifest>
    <item id="c1" href="chapter-01.xhtml" media-type="application/xhtml+xml"/>
    <item id="c2" href="chapter-02.xhtml" media-type="application/xhtml+xml"/>
    <item id="css" href="styles/book.css" media-type="text/css"/>
  </manifest>
  <spine>
    <itemref idref="c1"/>
    <itemref idref="c2"/>
  </spine>
</package>
```

The `metadata` block gives the book's identity. Each `item` in the manifest declares one file, with an `id` that other parts of the document use to refer to it, an `href` that gives its path relative to the OPF, and a `media-type` that states what kind of file it is. The `spine` then uses `itemref` entries, each pointing to a manifest item by its `idref`, to set the reading order. The distinction is important: the manifest says what exists, and the spine says what is read and in what sequence. A file can be in the manifest and absent from the spine, as an image or stylesheet normally is.

The `href` of a spine item is a name that will recur in later chapters. When the Reader needs to record where a user is in a book, the first piece of information is which spine item, identified by its `href`, the user is in. Chapter 3.4 builds on this.

### Navigation: NCX and the nav document

The spine gives reading order, but a reader also wants a table of contents with human-readable titles that jump to chapters. Epub 2 stored this in an XML file called the NCX, usually named `toc.ncx`. Epub 3 introduced a different method, a nav document, which is an ordinary XHTML page containing a list of links marked up as the book's table of contents. The two coexist because the Reader supports both Epub 2 and Epub 3, and because many Epub 3 files still include an NCX for compatibility with older reading software.

For an implementer, the point is that "the table of contents" is not a single, uniform thing. A reading engine must know both formats and choose among them. This is part of the reason the project uses an existing engine and does not parse epubs itself, as Chapter 3.2 explains.

### Reflowable and fixed layout

Most epubs are reflowable. The book's content is a flow of text and images with no fixed pages, and the reading app decides where each line and page break falls according to the screen size, the font, the font size, and the margins the user has chosen. This is the same principle that allows a web page to adapt to a window of any width, and it is the property that makes a font change or a dyslexia-friendly typeface possible. Changing the font does not alter the book. It alters how the same flow is laid out.

A smaller class of epubs uses fixed layout, in which every page is composed in advance with elements positioned at precise coordinates, similar to a page of a magazine or a children's picture book. Fixed-layout books cannot adapt to different screen sizes by reflowing and are usually displayed scaled to fit. The Reader is text-first, and reflowable books are its primary concern, so fixed-layout titles are not a priority. This is also why the architecture document describes images as acceptable but rich media as outside the focus.

Reflowable layout has a consequence that shapes much of the rest of the book. Because the pages change when the settings change, there is no stable notion of "page 112." A position in the book must be described in terms of the content, such as a place within a spine item, and not in terms of a page number or a scroll offset. Chapter 3.4 returns to this.

### The practical chaos of real epubs

The specification describes what a correct epub looks like, and many real epubs are not correct. Books are produced by a long chain of tools, from professional publishing software to hobbyist converters to scripts that turn web pages into books, and each leaves its own mistakes. A reading engine therefore spends much of its effort tolerating files that would be rejected by a strict validator.

Several categories of problem recur. The first concerns the `mimetype` file. The specification requires that it be the first entry in the ZIP archive and that it be stored uncompressed, so that tools can identify an epub by looking at fixed bytes at the start of the file. Some generators compress it or place it elsewhere, and a strict reader will refuse such a book even though the rest of it is fine.

The second category concerns the content files. XHTML follows the rules of XML, so every tag must be closed, attributes must be quoted, and special characters must be written in the correct way. HTML in a browser forgives such errors, but an XML parser does not, so a stray unclosed tag can make an entire chapter fail to load. Character encoding is related: epub content is expected to be UTF-8, and files that use another encoding, or that declare one and use another, produce garbled text. Whitespace is a further subtlety. Spaces and line breaks between inline elements can change how text renders, so a file that looks correct in one engine may show an unexpected gap or merged words in another.

The third category concerns styling. Publishers often embed CSS that was written for a particular reading application, and the same stylesheet may behave differently elsewhere. Some books fix the font, the margins, or the text color in ways that interfere with a reader's own settings, and an app that wants to offer a dyslexic font must decide how to handle a book that insists on its own. Other books depend on features a given engine does not support. The gap between the specification and what works in practice is wide, and it is the reason mature apps accumulate workarounds.

The fourth category concerns structure: books with a missing or broken table of contents, a spine that references files absent from the archive, or metadata that is empty or wrong. The app should degrade gracefully, perhaps by displaying a filename in place of a missing title, instead of refusing to open the book.

### Why the app copies imports into its own storage

An epub arrives from outside the app, through the system's file picker, from a folder such as Downloads or from an email attachment. Android does not hand the app a simple file path in that case. It hands over a content URI, an address that grants temporary and controlled access to the file, whose underlying location the app cannot rely on. Such addresses can stop working when the original file is moved, when a cache is cleared, or when the app is restarted.

For this reason, the Reader copies each imported epub into its own private storage, the sandbox, and always opens that copy. The architecture document calls this the copy-on-import policy. The cost is some extra disk space, which is small because text-based books are small. The benefit is reliability: the library entry continues to work no matter what the user does with the original file afterward. A user can delete the book from Downloads, reorganize their folders, or clear their email, and the Reader's copy remains. Chapter 4.1 describes the storage model in detail.

### Common pitfalls and gotchas

The most common structural pitfall is the ordering and compression of the `mimetype` file. A tool that builds epub files, or a script that repackages one, must write `mimetype` first and store it without compression. Standard archive utilities usually do not do this on their own, and the result is a file that looks correct but is rejected by strict readers. The reader may be tempted to blame the engine, when the cause is the archive.

A second pitfall is relying on file paths for imports. A path that works on a desktop or in an emulator may not exist on a phone, and a content URI that works at the moment of picking may not work later. Anything the app will need again must be copied into its sandbox at once, and the app should store its own path to that copy.

A third pitfall is trusting styling that looks right in a convenient tool. A book may look correct in a desktop application such as Calibre, which is permissive about CSS and markup, and then display differently in a stricter engine on a phone. Testing with a variety of real books on a real device is the only dependable check, and a suite of awkward sample files is among the most valuable assets a reading project can build.

The last pitfall is assuming the specification describes reality. Rules about well-formed XHTML, correct encodings, and tidy structure are all written down, and a significant share of books violate them. An engine and an app that handle imperfect files calmly will serve readers far better than one that insists on perfection.
