## Chapter 3.4 — Locators, progress, and highlights

### Key vocabulary

A **locator** is a structured description of a place in a publication, and **locator JSON** is that description written out as text so it can be stored. **CFI**, short for Canonical Fragment Identifier, is epub's own standard string for pointing to an exact spot inside a book's content. **Progression** is a number between zero and one that says how far through a content file, or through the whole book, a position lies. An **`href`** is the path of the content file in which the position falls. A **snippet** is a short piece of plain text saved alongside a highlight so the app can show or search it without opening the book. **Reflow** is the re-laying out of text that happens when the font, size, or margins change.

### The problem: where is the reader?

Every reading app must answer a deceptively simple question: where is the reader right now? The answer has to be saved when the reader closes the book and used to reopen it in the same place. It also has to anchor every highlight, so that a passage the reader marked stays marked.

On paper the answer is a page number, and many people carry that intuition into software. It fails here for the reason Chapter 3.1 gave. A reflowable book has no fixed pages. On a small phone with a large font, a chapter might fill sixty screens, and on a larger phone with a small font, thirty. The same sentence sits on a different page for each combination, and it moves whenever the reader adjusts a setting. A page number recorded under one setting is wrong under another.

The scroll position has the same flaw in a different form. It is a count of pixels from the top of some content, and the number of pixels to any given sentence changes whenever the layout does. Any position expressed in terms of the screen, whether pages, pixels, or coordinates, is a measurement of the layout, and layouts are temporary.

What remains stable is the content itself. The book's text does not change when the font does. A position that is described in terms of the content, such as "in this file, at this point in the text," stays correct through every change of layout. This is a logical position, as opposed to a physical one, and it is the foundation of everything in this chapter.

### What a locator contains

Readium's way of describing a logical position is the locator, which Chapter 3.2 introduced. It is a small object that a reading engine produces whenever it needs to say where the reader is, and that it accepts whenever it is asked to go somewhere. A fuller illustrative example follows.

```json
{
  "href": "chapter-02.xhtml",
  "type": "application/xhtml+xml",
  "title": "The Crossing",
  "locations": {
    "progression": 0.42,
    "totalProgression": 0.18,
    "position": 37,
    "fragments": ["epubcfi(/4/2/10/1:15)"]
  },
  "text": {
    "before": "They reached the river at ",
    "highlight": "dawn",
    "after": ", and the water was still."
  }
}
```

Each field answers a part of the question. The `href` names the spine item, the content file, in which the position falls, and it is the coarsest piece of the address. The `title` is the human-readable chapter name, which is useful for display. Inside `locations`, the `progression` gives the position within that file, and `totalProgression` gives the position within the whole book, which is the figure a progress bar would show. The `position` is an index into a list of positions that Readium computes for the book, a stable number that is similar to a page number but is derived from the book's content and not from the screen. The `fragments` entry holds a more precise pointer, here a CFI, which can identify a spot down to a single character. The optional `text` block holds a few words of context around the position, which helps the engine find the spot again if the other information is imprecise.

Not every locator carries every field. A locator for a reader's current position may need only the `href` and a progression, while a locator for a highlight needs enough precision to identify the exact passage. The engine fills in what it can, and the app stores the object it receives whole.

### CFI: a concept inside locators

The epub standard has its own way of pointing to a place in a book, the CFI. A CFI is a string that describes a path through the structure of a content file, a series of steps down through nested elements, ending at a character offset. It is precise, and because it refers to structure and not to layout, it also survives a change of font.

A newcomer might expect an app to choose between locators and CFIs, but they are not rivals. In Readium, a CFI commonly appears as one of the values inside a locator, among the `fragments`, and the locator is the larger, richer structure that the engine reads and writes. The architecture document makes the point that a CFI is not a separate coordinate system to maintain in parallel. Storing a CFI alone made sense for the epub.js library the team decided against, but with Readium it would be redundant, since the locator already contains it. A CFI would become useful on its own only if the app needed to exchange positions with other software, which is not a current requirement.

### Storing locators in SQLite

Because the locator is a structured object, the simplest and most faithful way to store it is as text. The object is serialized, which means converted to a JSON string, and kept in a text column of the database, which Chapter 4.2 describes. When the position is needed, the string is read back and turned again into an object, which is then handed to the engine through the adapter's `goTo` operation.

The architecture document records the reasoning in a comparison. Readium locator JSON works with Readium's own navigation and highlight functions directly, so there is nothing to convert, and the engine was designed for exactly the case of a reader resizing the text. A CFI string alone may work, but needs conversion and, for a highlight covering a range, would need two of them. A pixel or page index becomes unreliable after any reflow. For storage and backup, a single JSON value per position or highlight is simple and portable.

The same text column can hold the position that marks where the reader left off and the locators that anchor highlights. Each is a locator, stored the same way, which keeps the model small. The adapter is the only code that produces or interprets them, so the rest of the app treats stored locators as values to save and return.

### Highlights at scale

A highlight is a marked range of text, and in the Reader it is expected to be a heavily used feature. A reader may mark dozens of passages in a single book and change the font size several times along the way. Each highlight must remain attached to the same words throughout.

The approach follows from everything above. When the reader selects a passage and marks it, the engine produces a locator that describes the selected range in terms of the content. The app stores that locator against the book. When the book is opened later, or the layout changes, the app gives the stored locators back to the engine, which finds the described passages in the new layout and draws the highlights there. The app never records where on the screen a highlight was drawn, because that would be a fact about one layout only.

The architecture document notes one open detail. Depending on how `react-native-readium` represents a selected range, a highlight may be a single locator or a pair marking its start and end, and the schema may gain a second locator column once the first integration shows which it is. This is an honest uncertainty, and it illustrates why the team treats the first integration as an experiment.

The optional snippet is a separate matter. A list of highlights, a search over them, or a notes view needs to show the highlighted words without opening the book and asking the engine to locate them. For this, the app may store a short piece of plain text copied at the moment of highlighting, in its own column. The snippet is for display and search only. It is never used to find the passage, because that is the locator's job, and the two should not be confused.

### The acceptance test

The architecture document defines success for this part of the system in a concrete scenario, which makes the abstract ideas testable. The reader opens a book, highlights a passage, and changes the dyslexic font and the text size, twice. The reader then closes the book and reopens it. The test passes if the reader's position and the highlight both land on the same passage as before, on a real device.

This scenario exercises every idea in the chapter at once. The font and size changes force reflow, which would break any position tied to the layout. Closing and reopening forces the position to travel through storage and back. The highlight proves that ranges, and not only single points, survive. If the test passes, the logical-position approach is working. If it fails, the failure is informative, because it points to either the locator being stored incorrectly or the adapter passing it back incorrectly, the two places to look.

### Common pitfalls and gotchas

The first pitfall is thinking in page numbers. Product conversations naturally refer to pages, as in "resume on page 112" or "show a book's length in pages," and it is easy for such language to leak into the data model. A page number is a property of one layout. If a number is shown to the reader, it should be derived from the book's position data, and never be stored as the source of truth.

The second pitfall is edition swaps. A locator describes a place in a specific file. If the reader replaces a book with a different edition of the same title, a corrected reprint or a different publisher's file, the content may differ, and the stored locators may point to the wrong place or to nothing. The architecture document marks this as a tradeoff the team accepted, and notes that a file hash or edition identifier is left for later. In the meantime, the app should be prepared for a locator that does not resolve, and avoid failing when it does.

The third pitfall is the malformed epub. Locators depend on the engine's ability to make sense of the book's structure, and a book with broken XHTML, a damaged spine, or inconsistent content may produce locators that cannot be matched again later. Chapter 3.1 described how common such files are. The practical response is to test with imperfect books, and to make sure that a position that cannot be restored degrades to something sensible, such as the start of the nearest chapter.

The last pitfall is misusing the snippet. A snippet is convenient, and a developer may be tempted to use it to find a highlight by searching the book's text for it. Text can repeat, and the same sentence may appear many times, so the snippet is unreliable as an address. It should remain a display aid, and the locator should remain the only means of finding the passage.
