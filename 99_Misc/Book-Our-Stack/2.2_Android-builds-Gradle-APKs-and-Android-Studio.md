## Chapter 2.2 — Android builds: Gradle, APKs, and what Android Studio is for

### Key vocabulary

An **APK**, short for Android Package, is the single file that contains an installed Android app: its compiled code, images, fonts, and settings. **Gradle** is the build system that assembles the project's many pieces into an APK. A **keystore** is a file that holds the cryptographic key used to sign an app. **`minSdkVersion`** is the oldest version of Android the app agrees to run on. **`targetSdkVersion`** is the version of Android the app has been written and tested against, which tells the system which behaviors to apply. **`compileSdkVersion`** is the version of Android's programming interfaces that the code is compiled against. The **SDK**, or software development kit, is the collection of libraries, tools, and platform files that Android development requires.

### What an APK is

When a user installs an app on an Android phone, the phone receives one file, and that file is the APK. It is in fact a ZIP archive with a different extension, and opening one reveals a familiar structure of folders and files. Inside are the app's compiled code, its images and fonts, a manifest file that declares the app's name and permissions, the native libraries the app depends on, and the JavaScript bundle that Metro produced for the React Native layer. Everything the phone needs to run the app is in this one container.

This is the endpoint of the process that Chapter 2.1 began. The editor, Metro, and Expo exist to produce code, and the build turns that code into something a phone can install. A developer who has only worked on the web has no direct equivalent, because a website is delivered by a server and never installed. An APK is closer to a desktop installer, with the difference that it is delivered to a device that may be a different make and model from the one it was built on.

### Debug and release builds

The same project can be built in two forms. A **debug build** is made for development. It includes extra information that helps diagnose problems, is not optimized for size or speed, and is configured to connect to the development server so that Fast Refresh works. It is the kind of app produced by the `expo run:android` command in Chapter 2.1, and it is what the team installs during daily work.

A **release build** is made for use by readers. It has its debugging features removed, its code optimized and shrunk, and its JavaScript bundled inside the file so that no development computer is required. Release builds take longer to produce and are harder to debug, but they reflect how the app will behave in practice, including its speed and its memory use. A reading app that feels smooth in a debug build may feel different in a release build, and the reverse is occasionally true, so on-device testing of both is part of the team's practice.

### Signing, in plain language

Android requires that every app be signed before it can be installed. Signing means attaching a digital signature, produced with a private key, that proves the app came from a particular developer and has not been altered since. The phone checks the signature at installation, and it also checks that updates to an app are signed with the same key as the original. An update signed with a different key is rejected, which prevents someone else from replacing an installed app with a malicious one.

The key is stored in a file called a **keystore**, which is protected by a password. Debug builds are signed automatically with a generic key that the Android tools create, which is why a developer can install them without any special setup. Release builds should be signed with a key the project owns, and that key must be kept safe. If the key is lost, an app published under it can no longer be updated, and if the key leaks, others can sign apps that appear to come from the project. The architecture document lists signing hardening and Play Store release among the things deferred to later, so for the current phase it is sufficient to know that signing exists, that debug signing is automatic, and that a real keystore will become important when the project publishes to readers.

### Gradle: the orchestrator

A build involves many steps, and some of them must happen in a particular order. Kotlin and Java source files must be compiled. The JavaScript bundle must be created and included. Images, fonts, and other assets must be packaged. Native libraries, including Readium and the Expo modules, must be gathered and linked in. The manifest must be assembled from the settings of every library. The result must be compressed, optimized if it is a release build, and signed. Doing this by hand would be tedious and error-prone.

Gradle is the program that does it. It is a build system, which means a tool that reads a description of a project and works out which steps are needed and in what order. For Android it is the standard choice, and almost every Android app in the world is built with it. Gradle reads configuration files in the project's `android` folder, downloads the libraries the project depends on from public repositories, runs each step, and caches the results so that a second build, in which little has changed, is much faster than the first.

One of those files is `build.gradle`. A simplified, illustrative excerpt shows the sort of information it holds.

```groovy
android {
    compileSdkVersion 35

    defaultConfig {
        minSdkVersion 24
        targetSdkVersion 35
    }

    compileOptions {
        coreLibraryDesugaringEnabled true
    }
}

dependencies {
    coreLibraryDesugaring "com.android.tools:desugar_jdk_libs:2.0.4"
}
```

The `android` block holds settings about the app and the platform. The three SDK numbers, covered in the next section, are declared here. The `compileOptions` block turns on desugaring, a feature Chapter 2.1 mentioned in connection with Readium, which lets code written with newer Java features run on older phones. The `dependencies` block lists libraries to fetch, and the line shown supplies the support that desugaring needs. The specific numbers here are placeholders, and the real values come from Expo's defaults and from the requirements of Readium, as the architecture document describes. The practical lesson is that Gradle files are configuration, and that in Expo's managed workflow they are mostly produced by prebuild and its config plugins, not written by hand.

Gradle runs on Java, and the version matters. Readium requires JDK 17, where JDK is the Java Development Kit, the package that includes the Java compiler and runtime. If a computer has a different JDK installed as its default, the build can fail with an error that mentions an unsupported version, even though nothing is wrong with the project. Setting the right JDK for the project is one of the first steps in preparing a development machine.

### The three SDK versions

Three numbers in the build configuration cause frequent confusion, partly because their names are similar and partly because they answer different questions.

The `minSdkVersion` is the oldest version of Android on which the app is willing to be installed. Android versions are identified by numbers called API levels, and a phone running an older level than the minimum cannot install the app. A lower minimum reaches more phones, and a higher minimum allows the app to use newer features without workarounds. The team's guidance is to keep Expo's default and to raise it only if a concrete feature requires it.

The `targetSdkVersion` is the version of Android the app has been tested against. It is not a restriction. A phone running a newer Android than the target will still run the app. Instead, it tells the operating system which behavior to apply. Android changes its rules over time, for example by tightening what apps may do with files or notifications, and it generally applies the new rules only to apps that declare they target the new version. An app with a low target runs under older, looser rules, and the Play Store eventually refuses apps whose targets are too old.

The `compileSdkVersion` is the version of Android's programming interfaces that the code is compiled against. It determines which functions and classes the compiler knows exist. It does not change how the app behaves on a phone, but it must be new enough for every library the project uses. Readium's libraries require a compile version at or above a certain level, and the architecture document says to confirm the value during the Readium integration.

One way to remember the difference is by when each applies. The compile version applies when the code is built, the target version applies as rules at runtime, and the minimum version applies at installation.

### What Android Studio is for

Android Studio is the official integrated development environment for Android, published by Google. Many tutorials begin with it, which leads newcomers to assume that building an Android app means living inside it. In an Expo project this is not so. The daily work happens in a code editor and a terminal, and the app's code is JavaScript and TypeScript, which Android Studio adds little to.

What the team does need from Android Studio is what it installs. Through its SDK Manager, it downloads the Android SDK, the platform files and build tools required to compile for a given API level. It also supplies the emulator, a virtual Android phone that runs on the computer, and a command-line tool called `adb`, the Android Debug Bridge, which communicates with phones and emulators to install apps, copy files, and read logs. Even when developers never open its main window, they rely on the pieces it put on the machine.

The second use is diagnosis. When a build fails in a way that the terminal's messages do not explain, or when something in the generated `android` folder seems broken, Android Studio can open that folder and show the structure, errors, and settings in a form that is easier to inspect. It is, in this sense, a specialist's room that the team visits when a problem calls for it, and not the place where the app is made.

### Testing on a physical device

An emulator is convenient, but it is not the app's true environment. A reading app depends on how text is rendered, how fast pages turn, how selection feels under a finger, and how the app behaves under a real phone's memory limits. Emulators approximate these, and they run on a computer's processor and graphics hardware, not a phone's. The architecture document names a physical Android device as the primary validation target for this reason.

The standard way to put a build on a phone during development is to enable developer options on it, turn on USB debugging, and connect it to the computer. Once the phone is connected, `expo run:android` installs the debug build directly. A finished APK file can also be installed by copying it to the phone and opening it, which Android permits once the user allows installation from the source in question. Installing an app this way, outside an app store, is called sideloading, and it is how teammates and early testers will obtain builds before any store release.

### Common pitfalls and gotchas

The most common confusion is between the minimum and the target SDK versions. Raising the target does not stop older phones from installing the app, and lowering the minimum does not make the app behave as it did on older Android. The minimum controls who may install, and the target controls which platform rules apply. Changing either has consequences that are easy to overlook, so changes should be deliberate and confirmed in the build configuration, not assumed from memory.

The second pitfall is an inconsistent Java setup. A build that fails with a message about an unsupported class version, or about a Java version that does not match, usually means the wrong JDK is active. The fix lies in the environment, not in the code, and it is worth checking first.

The third concerns storage and web views, two topics around which myths persist. Older Android guidance warns about storage permissions and about the behavior of the system's WebView component, and a developer reading it might worry that the Reader inherits those problems. For the most part it does not. The app reads its own copy of each book from its private storage, which needs no broad storage permission, as Chapter 4.1 explains. And because Readium draws pages through a native engine instead of loading them in a WebView wrapped around a library like epub.js, problems that stem from WebView differences between phones are not the main concern. Treating old advice as universally applicable can send a team chasing problems it does not have.

The last pitfall is trusting the emulator alone. A build that looks correct on a fast desktop emulator may behave differently on a real phone, in memory use, in rendering, and in touch handling. Whatever the emulator shows, the phone has the final word.
