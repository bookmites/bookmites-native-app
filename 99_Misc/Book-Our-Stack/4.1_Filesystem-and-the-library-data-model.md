# Part IV — Data on the device

## Chapter 4.1 — Filesystem and the library data model

### Key vocabulary

A **book record** is the app's entry saying that a title is in the library, holding its metadata and its relationship to a file. A **user artifact** is anything the reader creates or accumulates while reading, such as a position, a highlight, or a note. A **`bookId`** is the app's own stable identifier for a book, used to link records and artifacts together. **`fileOnDevice`** is a field on the book record that says whether the epub file is currently stored on the phone. A **content URI** is the kind of address Android's file picker hands to an app, which grants access to a file without revealing a dependable path to it.

### Two kinds of storage, two kinds of data

The Reader keeps its data in two places on the phone, and understanding why is the key to this chapter. The first place is the filesystem, the phone's ordinary storage for files. The Reader uses a private area of it, discussed below, to hold the epub files themselves. The second place is the SQLite database, which Chapter 4.2 describes, and which holds structured information: the list of books, the reader's positions, the highlights, and the settings.

The division follows the nature of the data. An epub is a large, opaque file that the reading engine opens as a whole, and a database is poor at holding such things. A highlight or a reading position is a small, structured fact that the app needs to search, list, and update frequently, and a loose collection of files is poor at that. The architecture document describes these as storage layers, a statement of where bytes live, and it notes a third layer, an optional cloud backup, that is outside the current phase.

Alongside the question of where data lives is the question of what the data means, and here the architecture document draws a second distinction, between book records and user artifacts. The two views are different cuts through the same material. The first asks which technology holds a thing, and the second asks what kind of thing it is.

### Book records and user artifacts

A book record is the statement that "this title is in the library." It holds the book's metadata, such as title and author, a stable `bookId`, the location of the epub file in the app's storage if the file is present, and a flag, `fileOnDevice`, recording whether it is. It describes the book as an object the library knows about.

User artifacts are different in kind. They are the things a reader produces by reading: the position where they stopped, the passages they highlighted, and the notes they wrote. Later they will include conversations with an AI feature and attachments. Every artifact is tied to a book through its `bookId`, but it is the reader's own data and not part of the book.

The distinction matters because the two have different lifetimes and different value. A book file can be downloaded again, since it came from somewhere. A reader's highlights cannot be recovered if they are lost, since they exist nowhere else. The data model therefore treats artifacts as the more precious of the two, and its rules protect them. The `bookId` is the thread that ties them together, and because the app generates it, the link does not depend on the file's name, its path, or any detail that might change.

### Copy on import

When a reader adds a book, the app copies the chosen epub into its private storage and works from that copy from then on. This is the copy-on-import policy that Chapter 3.1 introduced from the point of view of the file format, and this section looks at it from the point of view of the filesystem.

On Android, each app has a private directory that belongs to it alone. Other apps cannot read it, the user does not see it in the file manager, and the operating system removes it when the app is uninstalled. This is the sandbox. Storing books there has several advantages. The app needs no special permission to read and write its own directory, the files cannot be moved or deleted by accident through other apps, and the app controls the path completely, so it can arrange files in whatever way suits it, such as one folder per `bookId`.

The alternative would be to store only a reference to the file the reader picked. That saves disk space and was considered, but the mobile setting makes it risky. The reader might pick a file from Downloads, an email attachment, or a cloud drive, and the original can move, disappear, or become unreachable without the app being told. The library entry would then point to nothing. Copying removes that fragility at the price of some extra storage, which is modest because text-based books are small.

### The file picker and content URIs

The system's file picker, which Expo provides access to through a document-picker module, does not return a simple file path on Android. It returns a content URI, an address that identifies the file through the operating system's content-sharing system. The address grants the app permission to read the file, often only temporarily, and it hides the file's real location, which could be on internal storage, on an SD card, or inside another app's data.

This design is part of Android's scoped storage model, in which apps are deliberately kept from roaming across the whole filesystem. For a book reader, the effect is mostly helpful. The app does not need a broad permission to read the user's files. It asks the user to pick one, receives access to it, and copies it. After the copy, the content URI is no longer needed, and the app deals only with its own path.

The import sequence can be summarized in prose. The reader taps to add a book, and the system picker opens. The reader chooses a file and the app receives a content URI. The app creates a new `bookId`, copies the file's bytes into its private directory at a path derived from that identifier, and reads the epub's metadata. Finally, it inserts a book record into the database with `fileOnDevice` set to true. Chapter 5.1 follows this flow end to end.

### Removing a file without losing the reading data

The separation of records and artifacts pays off in a feature that the product requires. A reader may wish to free space by removing a book's file while keeping their progress and highlights, in case they return to the book later. The data model supports this directly.

When the reader chooses to remove the file, the app deletes the epub from private storage and updates the book record, setting `fileOnDevice` to false and clearing the stored path. It does nothing to the artifacts. The book stays in the library, shown as not downloaded, with its position and highlights intact in the database. If the reader later provides the file again, the app copies it in, sets the flag back, and reading continues where it left off.

Removing the book entirely is a separate and more serious action. Only when the reader explicitly deletes the book from the library does the app delete the artifacts as well. The architecture document is explicit that deleting the file does not cascade into deleting highlights or progress, and that removal of artifacts happens only on a deliberate request. The two operations carry different warnings in the interface, because they have different consequences.

An illustrative sketch of the record shows how the flag fits in.

```ts
type BookRecord = {
  bookId: string;
  title: string;
  author: string | null;
  filePath: string | null;
  fileOnDevice: boolean;
};
```

The `bookId` is the identifier that artifacts will refer to. The `title` and `author` are metadata, and the author may be absent, which the type expresses as `string | null`. The `filePath` is the location of the app's copy and is empty when no file is present. The `fileOnDevice` flag states directly whether the file exists, so that screens can show the right state without checking the disk. The names are illustrative, and the real fields and table names remain to be settled, as the architecture document notes.

### Common pitfalls and gotchas

The first pitfall is reference-only imports. Remembering a picked file's address and opening it later seems to work during development, because the file is still where it was left, and fails for real readers when the file moves or the address expires. The failure appears long after the import, which makes it hard to trace. Copying at the moment of import is the reliable approach.

The second pitfall is deleting too much. A function that removes a book's file and, for convenience, also removes everything with the matching `bookId` will destroy highlights and progress that the reader expected to keep. The two operations should be separate functions with clear names, and the database relationships should not be configured to remove artifacts automatically when a file is removed. It is much easier to add a deliberate full deletion than to recover data deleted by mistake.

The third is treating the stored path as permanent. The app's private directory is stable, but the full path to it can change between versions of the operating system or after a restore. A safer habit is to store a path relative to the app's storage root, or to rebuild the path from the `bookId` when it is needed, and not to assume an absolute path saved last month is still valid.

The last pitfall is the assumption that a flag and the disk always agree. If the app is interrupted during an import, or the system clears storage under pressure, the record might say a file is present when it is not. A careful app checks that the file exists when opening a book and recovers gracefully, by marking the record accordingly and offering to import again, and not by crashing.
