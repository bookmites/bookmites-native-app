## Chapter 1.2 — From React on the web to React Native

### Key vocabulary

A **component** is a reusable piece of user interface, written as a function, that returns a description of what should appear on screen. **JSX** is the syntax that lets that description look like HTML tags inside JavaScript or TypeScript. **Props** are the inputs a component receives from whoever uses it, and **state** is information a component remembers and can change over time. The **bridge** is the boundary across which the JavaScript layer and the native layer exchange messages, and the term is used loosely here to cover how React Native connects the two. **Metro** is the program that gathers an app's JavaScript into a bundle and serves it to the app during development. A **screen** is a full-page view in the app, such as the library or the reader, while a **route** is the named location that navigation code uses to find and show a screen.

### What React is, in web terms

React is a library for building user interfaces out of components, and it was invented for the web before it was applied to phones. Understanding it is the key to understanding React Native, because React Native is not a different way of thinking. It is the same way of thinking pointed at a different target.

A component is the basic unit. Where a web developer might once have written a chunk of HTML for a book card and then used a script to fill in the title, React lets the developer write a function that takes the title and returns the card. The function can be used anywhere, as many times as needed, with different information each time. The following example shows a book card written the way the Reader's code would write it. It is illustrative, not taken from the repository.

```tsx
type BookCardProps = {
  title: string;
  author: string;
  onPress: () => void;
};

export function BookCard({ title, author, onPress }: BookCardProps) {
  return (
    <Pressable onPress={onPress}>
      <Text>{title}</Text>
      <Text>{author}</Text>
    </Pressable>
  );
}
```

The first block, `BookCardProps`, is TypeScript's way of declaring what the component expects to receive: a title, an author, and a function to run when the card is tapped. Those inputs are the component's props. The `BookCard` function receives them and returns a description of the interface in JSX. The curly braces inside the JSX mean "insert the value of this JavaScript expression here," which is how `{title}` becomes the actual title. Nothing in this function draws pixels directly. It describes what should exist, and React is responsible for making the screen match that description.

State is what lets a component change. If a component needs to remember whether a menu is open or what the user has typed, it holds that in state, and when the state changes React runs the component again and updates the screen to match the new description. The developer never writes instructions such as "find the element and change its text." The developer writes what the screen should look like for a given state, and React works out the difference. This is why React feels different from older web techniques, and it is the same on the phone as in the browser.

One more idea carries over directly: components can contain other components. A library screen contains a list, the list contains book cards, and each card contains text. A tree of components describes the entire interface, and React walks that tree. The language of parents, children, and nesting that a web designer already uses for HTML applies without change.

### What changes on a phone

If the component model is the same, the difference lies in what the components turn into. On the web, React produces elements in the Document Object Model, or DOM, which is the browser's internal tree of the page. A `<div>` becomes a rectangle in a web page, and a stylesheet decides how it looks. A phone has no browser and no DOM. React Native instead produces native views, the building blocks that Android and iOS themselves use to draw interfaces. When the code above renders a `Text` component, Android creates a genuine `TextView`, the same object that a handwritten Kotlin app would use.

This is why the tags are different. In place of `<div>`, React Native offers `View`, a plain rectangular container. In place of `<p>`, `<span>`, and heading tags, it offers `Text`, and all visible text must live inside a `Text` component. In place of `<button>` it offers `Pressable`, a wrapper that makes anything tappable. In place of `<img>` it offers `Image`, and for long scrolling collections it offers list components that draw only the items currently on screen. The vocabulary is smaller than HTML's, and each item maps to something real on the phone.

Styling follows the same pattern. React Native has no CSS files and no cascade. Styles are written as JavaScript objects and attached to individual components, and they borrow the names and spirit of CSS properties, with differences in spelling such as `backgroundColor` in place of `background-color`. Layout uses a model called Flexbox, which a web designer may know, but with a different default: React Native containers arrange their children in a column, where the web's default is a row. Sizes are expressed in density-independent units rather than pixels, so the same number looks about the same physical size on phones with very different screen sharpness. Most importantly, styles are not inherited. Setting a font color on a container does not change the text inside it, because each `Text` component must be styled itself or must be nested within another `Text`. This is the behavior that most often surprises people who come from the web.

The result is that web intuition about structure is a good guide and web intuition about styling is only a partial one. The arrangement of boxes, spacing, and hierarchy a designer draws in a tool such as Figma translates well. The mechanics of how a rule reaches an element do not.

Touch replaces the mouse. There is no hover state, because a finger does not hover, and there is no right-click. Interactions include taps, long presses, swipes, and drags, and the components that detect them behave differently from a web click handler. A tap target also needs to be large enough for a thumb, which is a design concern with a technical consequence: the clickable area is something the code must make big enough, not something the browser pads.

### Navigation: screens and routes

A website navigates by changing the address, and each page is a separate document. A phone app is a single running program, and moving between its screens is something the app's own code does. A **screen** is one full view, such as the library, the reader, or a settings page. A **route** is the name by which navigation code refers to a screen, much like a path in a URL, so that code can say "go to the reader and show this book."

Phones add a habit with no web equivalent: the back gesture or back button, which users expect to return them to the previous screen, and which the app must handle consistently. Navigation libraries keep a stack of screens, pushing a new one on top when the user goes forward and removing the top one when the user goes back. The existence of that stack has practical effects. A screen lower in the stack may remain alive but hidden, holding its state, which is different from a web page that is discarded when the user leaves it. Chapter 2.3 describes how the repository organizes screens, and the architecture document can be consulted for the specific navigation library the team adopts.

### Metro and the bundlers you may know

A web developer who has used tools such as Webpack or Vite has already met a bundler. A bundler takes the many files of a modern project, resolves their imports, translates newer syntax (including JSX and TypeScript) into plain JavaScript, and combines them into files a browser can load. React Native has its own bundler, called Metro, which performs the same role for the phone.

The practical difference lies in who consumes the output. A web bundler's output is delivered to a browser. Metro's output is delivered to a running app, which contains a JavaScript engine to execute it. During development, Metro runs on the developer's computer and serves the bundle over the local network to the app on a phone or emulator. When a file changes, Metro rebuilds only what is needed and pushes the update, and the app's Fast Refresh feature swaps the new code in while keeping the screen's state. This is what makes the daily loop feel like web development: edit, save, and see the change within a second or two. For a finished app, the bundle is built once and packaged inside the APK, so the phone does not need a development computer at all.

### The bridge, at a high level

Chapter 1.1 described the two runtimes. The bridge is the name for how they talk. When React decides that a `Text` component should appear, the JavaScript side does not draw anything. It sends instructions across the boundary, which tell the native side to create a view, give it some text, and place it in a certain position. When a user taps, the native side detects the touch and sends an event back across the boundary, which React turns into a call to the component's `onPress` function.

Older versions of React Native implemented this with an asynchronous queue of serialized messages, which gave rise to the name. Current versions use a more direct mechanism that lets JavaScript hold references to native objects and call into them without as much conversion. The details are beyond what this book requires, and Chapter 3.2 mentions where such modules matter for Readium. The relevant point is conceptual: two separate worlds, with a limited and deliberate channel between them. Any work that requires crossing the channel has a cost, and any work that stays on one side is cheaper.

### Where HTML and CSS thinking helps, and where it misleads

Several habits from the web serve a React Native developer well. Thinking in nested boxes, understanding that content flows and containers size themselves around it, and separating structure from appearance all carry over. A designer who has worked with auto-layout in Figma will find Flexbox familiar. Familiarity with accessibility, such as giving controls meaningful labels so that screen readers can announce them, also applies, and matters for a reading app whose audience includes people who depend on assistive technology.

Other habits mislead. The assumption that any HTML tag has a counterpart is false, and so is the assumption that CSS rules cascade and inherit. The assumption that layout will respond to a window being resized, which is the foundation of responsive web design, applies differently, because a phone's screen size is fixed, though its orientation, font-size setting, and display scaling can change. And the assumption that everything is a document, with links, scroll, and text selection provided for free, is wrong: scrolling, selection, and links are each components or behaviors someone has to supply deliberately.

### Common pitfalls and gotchas

The most frequent mistake for web-trained developers is to write `<div>` and `<p>` and expect the browser's behavior. React Native will refuse to render them, and the error message usually points toward a missing or misplaced component. Related to this is placing raw text outside a `Text` component, which also fails. The remedy is to learn the small set of core components and to remember that every visible string belongs inside `Text`.

Layout surprises come next. Because the default direction is a column, a container's children stack vertically unless told otherwise, and because styles do not inherit, a font size set on a parent has no effect on its children. A view with no explicit size and no content may collapse to nothing and look as though it failed to render. Developers new to the platform often fix these problems by trial and error, but the faster remedy is to remember that every component carries its own style and that Flexbox is the only layout system.

The last pitfall concerns performance. A phone's JavaScript code runs on a single thread, which means one line of work at a time. If that thread is busy, for example by processing a large list, parsing a big file, or running a heavy calculation, it cannot respond to touches or update the screen, and the interface appears to stutter or freeze. The native side continues to draw, but it has no new instructions from JavaScript until the thread is free. This is why the architecture favors keeping work light on the JavaScript side, debouncing frequent saves, and letting the native engine handle the heavy lifting of laying out book pages. Chapters 3.2 and 4.2 return to this idea, and it is worth keeping in mind whenever someone asks why a seemingly small operation caused the app to hitch.
